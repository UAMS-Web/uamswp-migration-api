## Temporary plugin

**This plugin is temporary.** It is deleted when the migration completes. That shapes several decisions below — no activation hook, exactly one network option written (a hashed token, deliberately not removed on uninstall — see `docs/DECISIONS.md` D-063), no tables created, no runtime Composer dependency.

## Why this exists

Three findings retired WXR as the importer's source. They are the reason nearly every design rule below exists:

1. **Large sites cannot export.** WordPress' exporter builds the whole XML in one request; on `uamshealth.com` it does not complete. Pagination solves this by construction.
2. **WXR carries stale ACF values for `location` and `provider`.** Find-a-Doc disables `store_acf_values_in_core_meta`, so those values live only in ACF custom database tables while postmeta sits frozen. Reading through `acf_get_value()` returns current values with no write to production.
3. **WXR has no element for options.** Zero of 259 captured exports contain `<wp:option>`. Every site migrated to date silently dropped its settings.

## Design rules

These are load-bearing. Breaking one produces a well-formed response full of wrong data, which is this project's defining failure mode.

- **Raw, not curated.** Return stored values un-resolved and un-composed. No rendering, no system+local merge, no hardcoded section composition. The existing `wp/v2` syndication view is what happens otherwise, and it is lossy for migration.
- **Read through each plugin's own API, never raw SQL.** `acf_get_value()` for ACF, `GFAPI` for Gravity Forms, the `Frm*` models for Formidable. The plugin's API is the only version-safe reader of its own schema.
- **Never resolve an ACF field type.** `acf_get_field_type()` returns a `stdClass` placeholder for `maskfield` and `null` for `button` on this network — two shapes, so a guard for either misses the other. `includes/ACF/FieldReader.php` dispatches on the field *definition* (does it carry `sub_fields`?) and never asks a type for behavior, which makes the tolerance structural. `tests/Unit/AcfApiGuardTest.php` holds `includes/` to an allowlist of four ACF functions. See `docs/DECISIONS.md` D-031.
- **For ACF that means the value functions, never the REST layer.** `acf_get_value()`, `acf_get_field_groups()` and `acf_get_fields()` only. Nothing in `includes/rest-api/` is reachable from this namespace — it matches `/wp/v2/…` routes exclusively — it cannot address options pages at all, and `acf_format_value_for_rest()` is unguarded enough to raise a fatal on this network. Do not call it, and do not change any `show_in_rest` setting. See `docs/DECISIONS.md` D-024.
- **Never filter underscore-prefixed keys.** ACF field-key references (`_fieldname`, `_options_<field>`), navigation (`_menu_item_*`), and featured images (`_thumbnail_id`) all live behind that prefix. A blanket `NOT LIKE '\_%'` filter silently breaks all three — it is what core's own network site-settings screen does, and copying it loses data.
- **Both meta shapes on every record.** `meta` carries raw flat postmeta exactly as WXR would serialize it, so existing importers run unchanged; `acf` carries structured values, the only shape available for `location` and `provider`.
- **Order by ID, never by date.** A migration pages through a live site while editors work. Date ordering lets a record move between pages mid-run and be read twice or skipped. IDs are immutable.
- **No anonymous access, ever.** The API serves unpublished content and raw site settings.
- **Every response says which site answered it**, in `X-UAMSWP-Site` (D-079, scope corrected by D-080). `?site=` is optional and an omitted one is served from whatever site handled the request, so without the header a consumer that dropped it received a well-formed `200` from another site with nothing to check against. A new controller inherits this from `Site`; it is not per-route work. Errors carry it too over HTTP — and a refusal names the site being **read**, since the switch runs before the auth gate. Internal dispatch (`rest_do_request()`, WP-CLI, the Feature suite) never fires `rest_post_dispatch`, so an error there is unstamped.

## Architecture

**Why the namespace is gated rather than each route:** WordPress generates a namespace index route for every registered namespace and ships it with no permission callback. Per-route callbacks structurally cannot cover it, and it leaked the full route table anonymously until the gate landed. The gate also means no new controller can ship an unauthenticated route by forgetting a callback.

**Machine-to-machine access needs a constant nobody sets by accident.** `Auth` takes either a WordPress user holding the capability on the site being read, or a shared secret in `UAMSWP_MIGRATION_API_SECRET`, presented as `X-UAMSWP-Migration-Key`. Until that constant is defined the secret path is inert, and **every failure returns an identical `401`** — unset, mismatched, mistyped and correctly-refused are indistinguishable. `README.md` carries the procedure and the three-request verification, because the person setting it is usually a human under time pressure rather than an agent; don't duplicate it here.

**Defining it does not affect the suite.** `tests/bootstrap.php` reads the live `wp-config.php` for `DB_NAME` alone — to refuse a run that would drop the development database — and never loads it as PHP. That is what lets `test:feature` and `test:feature:secret` be two processes: the branch where no secret is configured must authorize nothing, and it is reachable only while the constant is undefined.

**The autoloader stays hand-rolled.** Composer is dev-time only — the plugin must run on a stock WordPress install with no `vendor/` directory.

## Toolchain

- **`npm run ci:local` is the gate; `composer ci` is a subset of it.** The chain is eight cost-ordered jobs — load guard, `composer validate`, cspell, Pint, Rector, PHPStan, Pest, Node's own test runner — run in a sibling worktree so your checkout never moves. `composer ci` runs three of them in place. The gap is not theoretical: cspell sat red on `main` across two merges because nothing ran it. Run the chain before opening a PR. See `.claude/skills/local-ci`.
- **Remote CI is gated on the org-level `RUN_REMOTE_CI` variable.** Actions minutes bill across every `UAMS-Web` repo, and this repo is private, so a run here spends the same pool `uams-statamic` draws on. When it is `false` every job reports `skipped` and the local runner is the whole gate. A `skipped` check is not a passing check. `main` is deliberately unprotected because a skipped required check stays pending forever — see `docs/DECISIONS.md` D-029. Superseded on 2026-10-25 by D-105: the repository is public, the organization variable does not reach it, and `main` requires the aggregate `CI` check.
- **The suite runs on PHP 8.2**, the deployment target, and on 8.4. That is why the toolchain sits on **Pest 3 / PHPUnit 11** rather than the current majors: WordPress' test case extends the Yoast polyfills, which top out at PHPUnit 12, so the newer stack could not boot WordPress at any PHP version. See `docs/DECISIONS.md` D-019 before proposing an upgrade.
- **`tests/Feature` needs a database**, created once with `mysql -e "CREATE DATABASE uamswp_migration_api_tests"`. It is dropped and rebuilt on every run, and `tests/bootstrap.php` refuses to start if the name matches the working install's.
- **`UAMSWP_MIGRATION_API_TESTS_GF_FIXTURES` runs the Gravity Forms fixture-parity test**, pointed at the importer's `src/Services/WordPressImport/Tests/Exports/GravityForms`. It imports a real committed export and asserts it reproduces through the API — fields, notifications, confirmations and conditional logic. Unset, it skips: those exports are production form definitions carrying real notification recipients, so they are not vendored here. See `docs/DECISIONS.md` D-043.
- **The suite loads Formidable Forms and Formidable Pro when the surrounding install has them**, and installs their tables itself — Formidable creates them on *activation*, and the bootstrap never activates anything, so it calls `FrmMigrate` once after WordPress is installed. Pro is not optional decoration: ~23% of the captured corpus uses Pro-tier field types, and child forms exist only because Pro creates them. `UAMSWP_MIGRATION_API_TESTS_FRM_FIXTURES` runs the fixture-parity test against the importer's committed exports. See `docs/DECISIONS.md` D-046.
- **The suite loads Gravity Forms when the surrounding install has it**, and skips the tests that need it when it does not — paid, not a Composer package, so CI never has it, exactly as with ACF PRO. It boots unaided and installs its own tables into the test database. `tests/Feature/Forms/GravityFormsGuardTest.php` reds a run that had it on disk and failed to load it, so the skip cannot become permanent by accident; that file and `GravityFormsEndpointTest.php` skip on opposite conditions so every branch is covered somewhere. Note the local chain does **not** take the plugin-absent branch — its worktree sits inside `wp-content/plugins`, so it finds the real plugin exactly as your checkout does; only remote CI takes that branch, and remote CI is gated off. See `docs/DECISIONS.md` D-044.
- **The suite loads ACF, preferring PRO.** The bootstrap takes ACF PRO from the surrounding install when it is there and the `wpackagist-plugin/advanced-custom-fields` dev dependency when it is not — so a developer's run gets `repeater` and `flexible_content` while CI, which can never have a paid plugin, still runs everything portable. A PRO-only test carries an explicit `skip()`, and `tests/Feature/ACF/AcfEditionGuardTest.php` reds a run that loaded free while PRO was on disk. See `docs/DECISIONS.md` D-030.
- **Never run two suites concurrently.** They share one test database; the collision produces failures that read exactly like real regressions.

- **PHPStan runs at `level: max`** with `bleedingEdge.neon`, over `includes/`, `config/` **and `tests/`**, and carries an explicit `phpVersion` range for the PHP 8.2 deployment target. That range stays load-bearing even though the suite now executes on 8.2: PHPStan parses with `nikic/php-parser` rather than the host interpreter, so a construct 8.2 cannot parse is invisible without it, and a parse error never reaches the test runner. See `docs/DECISIONS.md` D-013 and D-015.
- **Pint uses the `laravel` preset**, which is PSR-12 plus that preset's house style. Deliberate and settled: it unwinds Yoda conditions, prefers short arrays, and strips `@package` tags, all against WordPress Coding Standards. See `docs/DECISIONS.md` D-014. Do not relitigate.
- **American spelling** in all first-party prose, comments, and identifiers, enforced by `cspell.json`'s `"language": "en"`. A `project-words.txt` entry that overrides it needs a stated reason — tool vocabulary a gate itself runs, or generated/verbatim-quoted data that must mirror an external vocabulary, are the two known legitimate categories; anything else is a spelling to fix, not an entry to add.

## Working on this repo

- **Merged head branches are never deleted.** Every file link in a pull-request body is a head-branch blob URL, so deleting the branch 404s them permanently — 286 live links depend on it today. See `docs/DECISIONS.md` D-077.

## Running it locally

This is a WordPress plugin, so it needs a WordPress multisite to run in. If you do not already have one, the team's [`wp-to-herd`](https://github.com/UAMS-Web/uams-claude-skills/tree/main/wp-to-herd) skill stands one up in Laravel Herd on Windows or macOS, from either a Local by Flywheel directory or a production backup, and covers the multisite case specifically. It lives in [`UAMS-Web/uams-claude-skills`](https://github.com/UAMS-Web/uams-claude-skills), installed opt-in through that repo's `install.sh`.

The development network that `scripts/verify-site-scoping.php` and `scripts/verify-taxonomy-coverage.php` expect is that install; both are documented under *Known gaps* as verifications that cannot run on CI.

## Known gaps

- **Dropped term assignments are verified against the development network** (#73). `scripts/verify-taxonomy-coverage.php` reports every taxonomy that carries assignments on an exposed post type but is not itself exposed, per site, and exits non-zero so it can gate a migration rather than only inform one. The Feature suite cannot answer this: it runs against a rebuilt database with no term data, and `location`/`provider` are not registered in its process. The registration-shaped half that CAN run on CI is the guard in `tests/Feature/PostsEndpointTest.php`.
- **All three form plugins are served** — `/forms/gravity`, `/forms/formidable` and `/forms/ninja` (D-055). Ninja Forms is free, so it is a dev dependency loaded from `vendor/` and its tests never skip; the other two are paid and theirs do. The Ninja endpoint exists to serve the form **id**, which a `.nff` export structurally cannot carry.
- **Gravity Forms add-on feeds are served, and no real one has been read** (#80, D-056). `/forms/gravity/feeds` and `/forms/gravity/<id>/feeds` carry the configuration that says a form creates a WordPress user on submission — the one part of a form's behavior that never appears in an export, because feeds live in `gf_addon_feed` and `GFAPI::get_form()` does not read it. The development network has never had a feed add-on active, so `gf_addon_feed` does not exist there and the test bootstrap installs it; every assertion runs against fixtures this repo creates. The payload shape is proven and the content of a production feed is not. Feed `meta` is filtered through D-032's machinery, with one exemption that carries the whole endpoint: a value that is a bare field reference is never withheld by name, because User Registration stores `password` as the id of the field the password comes from and a name-only denylist withholds exactly the mapping a consumer needs.
- **Site switching is verified against the development network** (#12, D-049). That network carries three sites, and `scripts/verify-site-scoping.php` asserts the switch, the payload difference, restoration on the success path, and the `409` refusal against a genuinely flagged site — 14 assertions, no skips. It needs an install, so it never runs on CI; the Feature suite covers the same branches against a factory-built network on every run.
- **Posts, options, discovery and terms exist, and `nav_menu_item` is served by the posts endpoint.** Menus needed no endpoint of their own: `nav_menu_item` is an eligible post type and `nav_menu` an eligible taxonomy, so the whole `_menu_item_*` set and the menu slug already travel — `tests/Feature/NavMenuParityTest.php` is what proves it rather than assuming it (#9). Attachments (#8) and authors (#10) have since landed, and comments were dropped from scope deliberately rather than deferred. Gravity Forms (#11) and Formidable Forms (#1) definitions are both served, and **two of the three now have readers**: the importer sources Gravity definitions under `--source=api` (`wordpress-importer#809`) and Ninja definitions likewise (`#810`), both merged 2026-09-15. `/forms/formidable` is still read by nothing, ticketed as `wordpress-importer#811`. D-050 carries the history, including why these were built ahead of any consumer and the condition that produced this one. Ninja Forms is deliberately not built (#56, closed): the importer ships a complete `.nff` file flow, and forms are the weakest case for this API because WordPress exports them to files reliably. Entries are never served (#54, D-048).
- **Post-type and taxonomy registration is process-global, not per-site.** `/post-types` and `/taxonomies` refuse `?site=` for that reason (D-034); to ask site N what it registers, call site N's own REST root.
- **Form submissions are never served, and a guard holds that line (D-048).** Not a note: Ninja Forms stores submissions as the `nf_sub` post type, so adding one string to `config/defaults.php` would have served submitted data through `GET /posts/nf_sub` with no new code. `tests/Unit/FormEntryBoundaryTest.php` fails that edit and every `GFAPI` entry method. Note the boundary is narrower than it reads — the definitions already served carry notification recipient addresses.
- **The option denylist was reviewed against one site.** 1,223 options, and the patterns are kept broader than what fires there deliberately (D-032). A credential stored under an innocent name with an innocent-looking value is undetectable by construction — that is the accepted direction of a denylist.
- **Collection queries run with `suppress_filters => true` (D-045).** A migration read sees the raw table, not a plugin's view of it — GeoTargeting WP hooks `posts_where` to remove posts from the loop, and a read that silently omits records is this repo's defining failure mode. It is not total protection: `pre_get_posts` is an action and still runs.
- **Query cost per page is flat, but only measured to 27 records.** Priming the page's parents took a page of attachments from 77 queries to 48 and removed the per-record growth (D-045). Production, with a larger plugin set and two orders of magnitude more attachments, is unmeasured.
- **`GET /authors` reports the authors it cannot resolve** (D-047) — a post can outlive the account that wrote it, and core drops those silently. Measured at 1.20% of items across the captured corpus. `X-WP-Total` counts only servable authors; the orphans travel on `X-UAMSWP-Orphaned-Authors` and `X-UAMSWP-Orphaned-Author-Ids`.
- **PHPStan analyzes against WordPress stubs two minors ahead of production** — `^6.8` resolves to 6.9.4 while production runs 6.8.7 (D-051). Left alone deliberately: unlike the PHP version gap, the Feature suite boots the real install, so a 6.9-only call fails at runtime rather than only in analysis. Pinning to `~6.8.0` was tried and produces six errors that are all stub defects.
- **`modified_after` is unverified against a real editing window.** The suite proves it filters on the GMT column with fabricated timestamps; nothing has yet re-pulled a site while someone edited it. Five concrete ways it lost or invented records — a bare date inflating to `23:59:59`, a zone-qualified ISO timestamp shifted by the site's UTC offset, never-published records excluded permanently by their zeroed GMT column, a bound landing in a daylight-saving gap rolled an hour forward, and non-timestamps like `2026` or `Thursday` silently becoming bounds — were found and fixed (D-052), so the remaining gap is the live-editing case specifically, not the parameter's arithmetic. Note that two of those five were introduced *by the fix for the first three* and caught only by the pre-merge review.
- **Nothing mechanically blocks a merge to `main`.** CI reports; it does not gate, because branch protection and the `RUN_REMOTE_CI` kill-switch cannot both be on (D-029). The chain being run and read is the gate. Superseded on 2026-10-25 by D-105: the repository is public, the organization variable does not reach it, and `main` requires the aggregate `CI` check.
- **The remote `pest` job runs against a factory-built network, not a real one.** It installs a two-site test network from the WordPress test factory, like the local suite. That is by design — an Actions runner has no development install — and `scripts/verify-site-scoping.php` is what covers the real one (#12).

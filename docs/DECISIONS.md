# Decisions

The durable index of decisions that shape this plugin. Each entry states the **what**, the **why**, and the **alternative that was rejected** — terse by design. The full reasoning lives on the linked issue; this file exists so a decision can be found without reading the tracker, and so a settled question is visibly settled rather than quietly reopened.

**Add an entry when a decision constrains work beyond its own ticket.** A choice that affects only the change making it belongs in that change's PR body. When an entry becomes a standing rule for how the whole repo is built, it also gets a line in [`CLAUDE.md`](../CLAUDE.md) — keep the two consistent.

Entries are append-only in spirit: superseding one means adding a new entry that says so and marking the old one, not editing history.

## Why this plugin exists

### D-001 — Replace WXR with an API rather than repair the exporter

- **Decided** — build a standalone read-only plugin as the importer's data source.
- **Why** — three independent defects, none fixable in the export path. Large sites cannot export at all, because the core exporter builds the whole XML in one request and does not complete on `uamshealth.com`. WXR carries stale ACF values for `location` and `provider`, because Find-a-Doc disables `store_acf_values_in_core_meta` and those values live only in ACF custom database tables while postmeta sits frozen. And WXR has no element for options at all: zero of 259 captured exports contain `<wp:option>`, so every site migrated to date silently dropped its settings.
- **Rejected** — patching the exporter, which does not address the one-request limit; and re-enabling `store_acf_values_in_core_meta`, which is a write to production data in order to serve a read.
- **Ref** — [`wordpress-importer#358`](https://github.com/UAMS-Web/wordpress-importer/issues/358)

### D-002 — Serve all content, not only the Find-a-Doc post types

- **Decided** — the API is general-purpose across post types, taxonomies, options, attachments, menus, authors, comments, and the plugins that export their own files.
- **Why** — the breadth costs almost nothing once the plugin exists, and a Find-a-Doc-only API would need replacing the moment any other gap surfaced. The missing-options gap in D-001 is network-wide, not Find-a-Doc-specific.
- **Rejected** — scoping to the two affected post types.
- **Ref** — [`wordpress-importer#358`](https://github.com/UAMS-Web/wordpress-importer/issues/358)

### D-003 — This plugin is temporary

- **Decided** — it is deleted when the migration completes.
- **Why** — it exists to move data once. Treating it as permanent invites scope it should never carry.
- **Consequences** — no activation hook, no options written, no tables created, no runtime Composer dependency, no upgrade path.

## Data contract

### D-004 — Return raw values, never curated ones

- **Decided** — serve stored values un-resolved and un-composed: no rendering, no system+local merge, no hardcoded section composition.
- **Why** — curation is lossy in a way the consumer cannot undo, and every judgment made here has to be un-made on the other side. The public syndication view is what happens otherwise, and it is lossy for migration.
- **Rejected** — reusing the public REST shape.

### D-005 — Both meta shapes on every record

- **Decided** — each record carries `meta` (raw flat postmeta, exactly as WXR would serialize it) *and* `acf` (structured values read through `acf_get_value()`).
- **Why** — it decouples two changes that would otherwise have to land together. Existing importers run unchanged against `meta`, while `acf` is the only shape carrying current values for `location` and `provider`.
- **Rejected** — picking one shape, which forces the source switch and the importer rewrite into a single step.

### D-006 — Order by ID ascending, never by date

- **Decided** — every paginated endpoint orders by immutable ID.
- **Why** — a migration pages through a live site while editors work. Date ordering lets a record move between pages mid-run, so it is read twice or skipped — and a skipped record produces no error anywhere.
- **Rejected** — date ordering, which is the natural default and is wrong here.

### D-007 — Never filter underscore-prefixed keys

- **Decided** — no blanket `NOT LIKE '\_%'` anywhere.
- **Why** — ACF field-key references (`_fieldname`, `_options_<field>`), navigation (`_menu_item_*`) and featured images (`_thumbnail_id`) all live behind that prefix, so one filter silently breaks all three. Core's own network site-settings screen does exactly this.
- **Rejected** — the hygiene filter that looks obviously correct.

### D-008 — Read through each plugin's own API, never raw SQL

- **Decided** — `acf_get_value()` for ACF, `GFAPI` for Gravity Forms, the `Frm*` models for Formidable, `get_option()` for options.
- **Why** — a plugin's own API is the only version-safe reader of its own schema, and for `location` and `provider` it is the only reader that returns current values at all.
- **Rejected** — direct SQL against the database, which is faster to write and breaks silently on any upstream schema change.

## Security and request handling

### D-009 — No anonymous access, ever

- **Decided** — every route requires either a WordPress user holding the required capability, or a shared secret in `UAMSWP_MIGRATION_API_SECRET`.
- **Why** — the API serves unpublished content and raw site settings.

### D-010 — Gate the whole namespace, not each route

- **Decided** — authorization hangs off `rest_pre_dispatch` for the entire REST namespace rather than living only in per-route permission callbacks.
- **Why** — WordPress generates a namespace index route for every registered namespace and ships it with **no permission callback**. Per-route callbacks structurally cannot cover it, and it served the full route table anonymously until the gate landed. The gate also means no future controller can ship an unauthenticated route by forgetting a callback.
- **Rejected** — per-route callbacks alone. They are retained as defense in depth, not as the boundary.
- **Ref** — #2

### D-011 — Site switching runs before authorization

- **Decided** — `Site::switchForRequest()` at `rest_pre_dispatch` priority 10, `Auth::guardNamespace()` at priority 11.
- **Why** — capability checks must apply to the site being *read*, not the one handling the request. Reversing the order authorizes against the wrong site.
- **Ref** — #2

## Toolchain

### D-012 — Composer is dev-time only; the autoloader stays hand-rolled

- **Decided** — the plugin must run on a stock WordPress install with no `vendor/` directory.
- **Why** — it is deployed by copying a directory, and it has no third-party runtime dependencies.
- **Verified** — the plugin loads and serves with `vendor/` deleted.
- **Ref** — #14

### D-013 — PHPStan opens at `level: max` with `bleedingEdge`

- **Decided** — start at the ceiling rather than climbing to it.
- **Why** — the analyzer arrived when the codebase was a thousand lines old, so there was no legacy analysis debt to pay down; starting lower would mean choosing to accrue it. `bleedingEdge` ships inside `phpstan/phpstan`, so it costs no dependency and keeps the next major upgrade clean.
- **Rejected** — a staged climb, which is the right call only for a codebase that already carries debt.
- **Ref** — #14

### D-014 — Pint uses the `laravel` preset, not WordPress Coding Standards

- **Decided** — PSR-12 plus the preset's house style.
- **Why** — consistency across the organization's PHP was preferred to consistency with the platform's idiom. Chosen deliberately, with the costs known: it unwinds Yoda conditions, prefers short arrays, and strips `@package` tags, all against the WordPress Coding Standards.
- **Rejected** — the WordPress Coding Standards. Do not relitigate without new information.
- **Ref** — #14

### D-015 — PHPStan carries an explicit `phpVersion` range for the PHP 8.2 target

- **Decided** — `phpVersion: { min: 80200, max: 80400 }`.
- **Why** — left implicit, PHPStan infers a range from `composer.json` and does not report constructs unavailable at the floor: a typed class constant (PHP 8.3+) analyzed completely clean and would have been a parse error in production. PHPStan parses with `nikic/php-parser` rather than the host interpreter, so this stays load-bearing even now that the suite executes on 8.2 — a construct 8.2 cannot parse is still invisible without it.
- **Rejected** — a single `phpVersion: 80200`, which catches the same constructs but stops matching the `if.alwaysFalse` ignore for the runtime guard and reds the run.
- **Amended by D-019** — this entry originally justified itself as *the only* thing in the gate that knew about PHP 8.2, because the suite could not execute on the deployment target at all. That is no longer true. The reasoning above is the part that survived.
- **Ref** — #17, #15

### D-016 — Hook callbacks are never first-class callables

- **Decided** — `ArrayToFirstClassCallableRector` is confined to the sweep profile.
- **Why** — WordPress matches hook callbacks **by identity** for `remove_action()` and `has_action()`. A first-class callable builds a fresh `Closure` per evaluation, so the handle used to register can never equal the one used to remove, and hook removal silently stops working.
- **Ref** — #14

### D-017 — The PHP 8.2 runtime guard is never rewritten by Rector

- **Decided** — `UnwrapFutureCompatibleIfPhpVersionRector`, `RemovePhpVersionIdCheckRector` and `VersionCompareFuncCallToConstantRector` are skipped in both profiles, path-scoped to the plugin header.
- **Why** — all three reason from `composer.json`'s `^8.2`, conclude the branch is unreachable, and between them would delete the version test, the admin notice and the early return. The branch exists for the case that reasoning cannot model — a site downgraded underneath an already-active plugin — where the alternative is a fatal error instead of a notice.
- **Ref** — #14

### D-018 — Guidance is written for this repo, and copied only at the point of need

- **Decided** — `.claude/` carries only what applies here today, written without reference to any other repo. Anything that becomes relevant later is brought in at that point rather than held in advance.
- **Why** — guidance describing a repo you are not in is worse than no guidance, because an agent acts on it. Guidance carried speculatively also arrives stale, which is the failure it was meant to prevent.
- **Consequences** — the coverage-driver setup guide was deleted rather than reworked, since nothing here can use a coverage driver until #15 lands a suite worth mutating. #15 landed one, so `.claude/skills/coverage-driver` was written then, against what this repo actually needs — which turned out to be Xdebug rather than the PCOV the deleted guide described.
- **Ref** — #14, #17

## Testing

### D-019 — The test toolchain sits on Pest 3 / PHPUnit 11, not the current majors

- **Decided** — `pestphp/pest: ^3.8`, `phpunit/phpunit: ^11.5`, with `config.platform.php` pinned to `8.2.30`.
- **Why** — two independent ceilings, and the lower one is not about PHP at all. WordPress' test case extends `Yoast\PHPUnitPolyfills\TestCases\TestCase`, and the polyfills top out at **PHPUnit 12** (`^7.5 || ^8.0 || ^9.0 || ^11.0 || ^12.0` at 4.0.0 — note the absence of 10). Pest 5 pins PHPUnit 13, so the Feature suite could not have been built on the previous toolchain at any PHP version. Given a downgrade was forced, Pest 3 was chosen over Pest 4 because it is the last release supporting **PHP 8.2**, which makes the suite executable on the version production runs. The `platform` pin is what stops a later `composer update` on an 8.4 machine from silently climbing back out of range.
- **Rejected** — Pest 4 / PHPUnit 12 / PHP 8.3, the smallest step that works: it costs the same downgrade and buys nothing, since Pest 4's additions over 3 are browser testing (no frontend here) and refinements to mutation testing, which Pest 3 already ships.
- **Rejected** — `alleyinteractive/pest-plugin-wordpress`, which solves the same problem properly by replacing core's test case with **Mantle Testkit**. It pulls 13 packages and a WordPress framework into a plugin that is 8 source files, has no runtime dependencies by design (D-012), and is deleted when the migration completes (D-003). Also requires PHP 8.3.
- **Rejected** — `dingo-d/wp-pest` and the Brain Monkey approach generally. See D-021.
- **Consequences** — `pestphp/pest-plugin-phpstan` was dropped; it exists only for Pest 5. Its `$this`-binding resolver is replaced by typed helpers in `tests/Support/helpers.php` rather than by a suppression, and its `@internal`-class handling by one `identifier`-scoped ignore pinned to `tests/`.
- **Amended by D-092**: the toolchain this entry chose now holds only for the suite that boots WordPress, in its own setup under `tests/Integration/`, with `config.platform.php` at `8.4.27` (`8.4.1` when D-092 was decided; raised by D-109). `tests/Unit` moved to Pest 5. The polyfill ceiling recorded above is why the two could not share one setup.
- **Ref** — #15

### D-020 — WordPress' own test case is adapted, not replaced

- **Decided** — `tests/Support/WordPressTestCase.php` extends `WP_UnitTestCase` and overrides exactly two methods.
- **Why** — `expectDeprecated()` calls `PHPUnit\Util\Test::parseTestMethodAnnotations()` and `getName()`, both removed in PHPUnit 10. Scanning the whole of `wp-phpunit` found **that one call site** — nothing else in core's test suite touches a removed PHPUnit API — so a twelve-line override is the entire cost of running core's test case two majors forward. (`checkRequirements()` is overridden for a separate reason: its docblock names an annotation in prose, which PHPUnit's metadata parser reads as real metadata.)
- **Rejected** — pinning to PHPUnit 9 to match what WordPress supports, which would have meant Pest 1 (2021) and no mutation testing.
- **Ref** — #15

### D-021 — The Feature suite boots real WordPress, never a mocked one

- **Decided** — `wp-phpunit` against a real multisite install and a real database, with every REST test going through `rest_do_request()`.
- **Why** — the one real bug the scaffold shipped with was core's auto-generated namespace index route answering anonymously. Static analysis could not see it, reading the diff did not catch it, and a Brain Monkey suite would pass happily — the route exists and the callback returns fine. It took a dispatch against a booted WordPress. The suite's first run then found a **second** bug of the same shape (D-022).
- **Rejected** — Brain Monkey via `yoast/wp-test-utils`, which is the common recipe for Pest and WordPress and is faster to stand up. It mocks away the exact layer where this plugin's defects live.
- **Consequences** — the suite needs a database and cannot run in parallel against a shared one.
- **Ref** — #15, #2

### D-022 — The switched blog is restored on every dispatch exit, not just `rest_post_dispatch`

- **Decided** — `Site::register()` hooks the restore to `rest_pre_dispatch` (last priority), `rest_request_after_callbacks`, and `rest_post_dispatch`.
- **Why** — `rest_post_dispatch` fires only inside `WP_REST_Server::serve_request()`. `rest_do_request()` is `rest_get_server()->dispatch()`, which never reaches it, so every internal sub-request returned with the blog still switched and everything afterwards read the wrong site — the defining failure mode, a well-formed response full of wrong data. `dispatch()` has three exits and the original wiring covered none.
- **Found by** — the #15 suite on its first run, not by review.
- **Accepted gap** — a request into this namespace matching no route reaches none of the three hooks, and is left to the `shutdown` backstop.
- **Ref** — #15

### D-023 — Mutation testing is scoped to `Pagination`, `Config` and `Auth`

- **Decided** — `composer mutate` runs `--covered-only` against those three files by name, not against `includes/`.
- **Why** — **mutation cannot reach a class that is already loaded when the mutation runner starts**, and two of this plugin's classes are. `Plugin::boot()` calls `Site::register()` directly, so both `Plugin` and `Site` load during the test bootstrap; every other class is referenced only as a callable array (`[Auth::class, 'guardNamespace']`) or instantiated at `rest_api_init`, and loads later. A full run over `includes/` scores those two at **0.00%** — `Site` alone is 0 killed out of 63 — while manually deleting `switch_to_blog()` from the same file fails two tests immediately. Verified, not inferred: dumping `get_declared_classes()` at the end of the bootstrap returns exactly `Plugin` and `Site`.
- **Rejected** — running over all of `includes/` anyway. It takes 7 minutes, and it reports a permanent 0% for two files that are in fact tested. A score that cannot move is worse than no score: it reads as a standing indictment of the suite and trains everyone to ignore the number.
- **Rejected** — restructuring `Plugin::boot()` to register `Site`'s filters itself so the class loads lazily. It would make `Site` mutable, at the cost of moving hook ordering away from the class that owns it — and that ordering is load-bearing enough to be documented in `CLAUDE.md`. Contorting the design to suit a tool is the wrong trade.
- **Consequences** — `Site` and `Plugin` are covered by tests but not by mutation. The site-scoping tests are the compensating control, including the negative control run against the unfixed `Site.php`.
- **Measured** — 216 mutants over `includes/` in 415s. Scoped: `Pagination` 95.1%, `Auth` 90.0%, `Config` 69.4%.
- **Found** — the first `Pagination` run scored 78% and named three real gaps: both hardcoded bounds fallbacks, the `max(1, $max)` floor, and the `(int)` cast on query-string parameters. All three are now covered; the two remaining survivors are equivalent mutants.
- **Not decided** — a minimum score gate, and mutation in `composer ci`. The run takes minutes, and until the endpoints land any number measures only the scaffold.
- **Amended by D-092**: `composer mutate` runs from `tests/Integration/`'s Composer setup, where the v3 mutate plugin and both patches now live, against the same three classes.
- **Ref** — #15

## ACF integration

### D-024 — ACF's REST layer is not used; only its value and field-discovery functions

- **Decided** — read ACF through `acf_get_value()`, `acf_get_field_groups()` and `acf_get_fields()`. Nothing in `advanced-custom-fields-pro/includes/rest-api/` is used, `acf_format_value_for_rest()` is never called, and no `show_in_rest` setting is changed anywhere.
- **Why** — **ACF's REST layer structurally cannot serve a custom namespace.** `ACF_Rest_Request::build_supported_routes()` (`class-acf-rest-request.php:119-154`) builds match patterns for `/wp/v2/…` only, so for any route in this plugin's namespace `object_type` resolves to `null`, `ACF_Rest_Api::register_field()` bails at `:62`, and the `acf` property is never registered. Verified by parsing this plugin's routes through `ACF_Rest_Request` directly: `/wp/v2/posts/1` resolves to `post`/`post`, `/uamswp-migration/v1/posts` to `null`/`null`. The adopt-versus-build framing the spike opened with does not survive that — there is nothing reachable to adopt.
- **Why, independently** — three further findings, each sufficient on its own:
    - **It cannot address options at all.** Supported object types are post, term, user and comment (`class-acf-rest-request.php:192-209`). `options_page` is the largest single location parameter on this network — **35 of 89 field groups**, against 16 for `post_type` — plus `block` (20) and `widget` (2). That is finding #3 in `CLAUDE.md`, the gap this project exists to close, sitting entirely outside the layer.
    - **It would need `show_in_rest` on all 89 field groups.** Three independent gates exist, not one: post type (`class-acf-rest-request.php:122`, `:219`), field group (`class-acf-rest-api.php:448`, `:513`) and field type (`:532`). The seven migration-relevant post types already carry `show_in_rest = true`, so that side effect is live; **0 of 89 field groups do**. Adopting means changing the live site's public ACF surface as a precondition.
    - **It would fatal on this network.** `acf_format_value_for_rest()` calls `$type->format_value_for_rest()` with no guard (`acf-rest-api-functions.php:74`), and `ACF_Rest_Api::get_fields()` filters top-level fields only — container formatters recurse into sub-fields unfiltered. `acf-maskfield` never calls `acf_register_field_type()`, so its type stays the `stdClass` placeholder that `acf_field::__construct()` registers via `acf_register_field_type_info()` (`class-acf-field.php:36`). Reproduced: `location` #3552 holds `location_phone_numbers` (repeater) containing `location_appointments_phone` (maskfield), and formatting it raises `Call to undefined method stdClass::format_value_for_rest()`. **7 of 89 field groups** contain such a field. Tracked separately in #21.
- **Rejected** — the `acf/rest/format_value_for_rest` filter as the route to raw values. It works: returning the unformatted 4th argument yielded byte-identical raw across **1,128 fields on 25 posts with zero mismatches**, and formatting never mutates the raw value despite `acf_field_repeater::format_value_for_rest()` iterating `foreach ( $value as &$row )` (0 mutations over 537 non-empty values). It is rejected because it is reachable only from a layer this plugin cannot reach, and because calling the formatter is what triggers the fatal above.
- **Rejected** — serving through `wp/v2` instead of a private namespace, which is what would make ACF's layer reachable. It gives up the namespace gate (D-010), the site parameter (D-011), pagination (D-006) and raw output (D-004) at once, and `light` formatting is lossy for migration regardless: every `clone` (170/170), `repeater` (75/75), `group` (15/15), `true_false` (105/105) and `number` (10/10) value observed differs from what is stored.
- **Consequences** — the value layer is hand-written, and `acf_get_store( 'values' )->reset()` must be called per record when paginating. ACF's layer does this at `class-acf-rest-api.php:245`; without it the store grew to **614 entries over 20 posts** (42 after one), which is unbounded across a page.
- **Verified** — the ACF Custom Database Tables routing that motivates all of this is real, and was finally observed rather than inferred. Reading `location` #82 through this plugin returns **`meta.location_about` = the frozen 1,377-character postmeta value** (what WXR would export) and **`acf.names.location_about` = the current value stored only in `wp_uamswp_locations`**, in one payload. That divergence is finding #2 in `CLAUDE.md`, and it is what WXR structurally cannot carry.
- **Why it took so long to see** — ACF CDT resolves its table map from a **cached PHP file**, `UAMSWP-Find-a-Doc/assets/json/acf-tables/.cache/_table_map.php`, and that file is committed to the Find-a-Doc repository in a stale state: last regenerated **2019-10-22**, while its source JSON moved on **2021-02-05**. The stale copy keys post types as `locations`/`physicians`; the registered types are `location`/`provider`. `TableMap::register_post_types()` reads the JSON value with no derivation, so a stale cache silently mis-keys every lookup, `has_table()` returns false, and **both** intercepts go quiet — `ACFGetFieldIntercept` and `ACFUpdateFieldIntercept` share the same gate. Production is corrected by hand after each deploy: clicking "Create/Update Tables" runs `update_tables()` *and* `rebuild_map_cache()`, which is why the manual step exists and why data goes visibly wrong until someone performs it. Production's on-disk map was inspected directly and carries the correct singular post types and 118 columns against the committed copy's 89. Tracked in #28 and, for the deploy that reverts it, upstream in `UAMSWP-Find-a-Doc`.
- **Consequences for this repo** — the development install ships in the post-deploy state, so ACF CDT is inert there until the same rebuild is run. It has been run: the map now resolves `location`/`provider` and both tables exist, empty, so reads fall back to postmeta exactly as production does between edits. Anyone rebuilding this environment from scratch has to repeat it, or the divergence above is unreproducible and every `location` read looks deceptively clean.
- **Ref** — #7, #4, #6, #21

### D-025 — The `acf` payload carries both the field-key and the field-name view

- **Decided** — structured ACF values are emitted twice: keyed by field key exactly as `acf_get_value()` returns them, and keyed by field name.
- **Why** — the two serve different masters and neither substitutes for the other. Field keys are what is stored, so the key view is the only one that satisfies D-004 without a transformation; ACF's own `light` format rewrites keys to names (`acf_field_clone::format_value_for_rest()` extracts `$sub_field['key']` and re-adds under `$sub_field['name']`, and repeater, group and flexible content do the same per row), which is a structural change, not formatting. But a field key is opaque — `field_5f3a2b1c` means nothing without the field-group definitions — while the flat `meta` payload already uses names (`home_slides_5_home_slide_title`), so the name view is what makes the two payloads cross-referenceable and what an importer maps to Statamic fields.
- **Rejected** — keys only. It is the strictest reading of D-004, and it pushes key resolution onto the importer for the two post types (`location`, `provider`) that have no usable postmeta to resolve against.
- **Rejected** — names only, matching ACF's REST output. It is the most usable single shape and it discards information: names can collide across field groups, keys cannot.
- **Consequences** — both views are free to compute, since holding the field array is what produces either. Payload size grows.
- **Ref** — #7, #4

### D-026 — Options carry the flat table *and* structured ACF values

- **Decided** — the options endpoint serves the whole `wp_options` table as specified, and adds a structured per-options-page view read through `acf_get_value( 'options', $field )`.
- **Why** — D-005 applied to options. The flat table is not lossy, but it is flat in the way WXR is: `remove_ontology_criteria` is stored as `"1"`, the repeater row count, with the rows themselves in numbered `options_remove_ontology_criteria_0_*` keys, while `acf_get_value( 'options', $field )` returns the assembled structure. Existing importers read the flat shape and must keep working; the structured shape is what a new consumer can use without reimplementing ACF's row assembly.
- **Why it is reachable at all** — reading options through ACF needs none of the REST layer that D-024 rejects. Confirmed against the nine options pages on this network, all of which use `post_id = 'options'`.
- **Consequences** — expands #6 beyond its original single-query scope.
- **Ref** — #7, #6

## Continuous integration

### D-027 — CI runs the whole chain on PHP 8.2, the deployment target

- **Decided** — every job in `.github/workflows/ci.yml`, and `scripts/local-ci.mjs` locally, runs on **PHP 8.2**. Locally the runner prefers Herd's version-pinned `php82` binary, so a run targets 8.2 even when the default Herd PHP is 8.4.
- **Why** — production runs 8.2.30, and running the deployment target is strictly stronger than analyzing for it. #18 specified the opposite — run on 8.4 and let PHPStan's `phpVersion` range hold the 8.2 line alone — on the premise that the test toolchain had a hard 8.4 floor (`pestphp/pest` v5 requires `^8.4`, `phpunit/phpunit` 13 requires `>=8.4.1`). D-019 had already removed that floor: the toolchain came down to Pest 3 / PHPUnit 11 precisely so the suite could execute on the version production runs, and `config.platform.php` is pinned to `8.2.30`. Verified rather than assumed — both suites pass under `php82`.
- **Rejected** — the `php -l`-on-8.2 lint job #18 floated as a second line of defense. It exists to catch what an 8.4 runner cannot parse-check for 8.2; running the chain itself on 8.2 subsumes it.
- **Rejected** — a version matrix (8.2/8.3/8.4). Minutes bill org-wide, and nothing deploys to 8.3 or 8.4. PHPStan's `phpVersion: {min: 80200, max: 80400}` (D-015) still covers the 8.4 end, which is what the local toolchain also runs on.
- **Consequences** — `tests/Unit/CiParityTest.php` pins `8.2` by name, so raising it is a deliberate edit rather than a quiet one.
- **Superseded by D-092**: the chain runs on PHP 8.4, and a `lint-floor` job parses every shipped file on PHP 8.2. The lint job rejected above is what holds the floor now that no suite runs on it.
- **Ref** — #18, #15

### D-028 — Local and remote CI are hand-maintained mirrors, held together by a hook and a test

- **Decided** — `.github/workflows/ci.yml` and `scripts/local-ci.mjs` run the same seven-job cost-ordered chain and are kept in step by hand: `# PARITY:` markers in both, a `.githooks/pre-commit` co-change gate wired by `composer install`, and `tests/Unit/CiParityTest.php`.
- **Why** — the local runner is not a convenience. While `RUN_REMOTE_CI` is off — the normal operating mode for months at a time — it is the only gate there is, so a remote workflow without a local mirror means no validation at all during a budget freeze. Two mirrors with no shared source of truth drift silently, and the drift is invisible in the way that matters: each file keeps working alone.
- **Rejected** — generating one from the other. They are not byte-comparable and should not be: CI runs `vendor/bin/pint` where the runner runs `php vendor/bin/pint` (to pin which interpreter analyzes), and the runner carries local-only steps a fresh-checkout runner has no need of — branch reconciliation against `origin`, and handing the run to the branch's own copy of itself so a PR that adds a job has that job actually run.
- **The chain is eight jobs now, not the seven this entry was written against.** `node-test` was added by #150 and carries no decision entry of its own, so this remains the only description of the chain's composition in the log and it had aged into the only wrong one. The "Decided" line above is left as written — it records what was decided, and there were seven jobs then — and this bullet carries the correction rather than rewriting history. Corrected under #171, which found it in a sweep for exactly this.
- **Consequences** — every job change is a two-file change. The parity test reads `ALL_JOBS` and `CHAIN` out of the runner textually, so those stay single-line array literals; the pre-commit gate can be bypassed with `--no-verify`, deliberately, because legitimate one-sided edits exist.
- **Superseded in part by D-091**: the local mirror is now `local-ci.json`, run by the shared runner, not `scripts/local-ci.mjs`. The hook, the markers and the parity test remain; they compare `ci.yml` with `local-ci.json`.

### D-031 — ACF values are dispatched on the field definition's shape, never on its type

- **Decided** — `UAMSWP\MigrationAPI\ACF\FieldReader` treats any field carrying `sub_fields` (or `layouts[*]['sub_fields']`) as a container and recurses, whatever `$field['type']` says. No field-type object is obtained anywhere in `includes/`; `tests/Unit/AcfApiGuardTest.php` enforces that as an allowlist of four ACF functions.
- **Why** — `acf_get_field_type()` does not always return an `acf_field`, and it fails in **two different shapes**: `maskfield` resolves to the `stdClass` placeholder `acf_field::__construct()` registers, and `button` resolves to `null`. A guard written for either alone misses the other. Dispatching on the definition needs neither, so the tolerance is structural rather than a patch — and a field type added to ACF tomorrow needs no change. Verified against live `location` #3552: the reader returns `location_appointments_phone` as `501-686-6080` from inside the `location_phone_numbers` repeater, while `acf_format_value_for_rest()` on the identical value raises `Call to undefined method stdClass::format_value_for_rest()`.
- **Rejected** — resolving the type and guarding the result with `instanceof acf_field`. It works, and it puts a lookup in the code whose every use is unsafe; the next person to add a call site has to re-derive why. Banning the lookup is mechanical, so there is no judgment call about which method is safe.
- **Consequences** — the read returns three things, not two: `keys`, `names`, and `collisions`. Field names can collide across field groups where keys cannot (D-025), so the name view keeps the first occurrence and **names** the loser rather than overwriting it in silence. The key view stays lossless either way. `acf_get_store( 'values' )->reset()` runs at the end of every read — measured across live `location` records, the store is empty after each.
- **Ref** — #21, #7, #4

### D-032 — The option denylist is reviewed against production, exempts `_options_*`, and judges values as well as names

- **Decided** — `config/defaults.php` carries a denylist of **bare word suffixes** (`%key`, `%token`, `%secret`, `%license`, `%credential`) rather than separator-specific ones; an option beginning `_options_` is never denied, as a rule in `OptionsPayload`; and `OptionsPayload` **additionally withholds any value whose shape reads as a secret** — an unbroken run of hex or base64, a JWT, or a known vendor prefix — whatever the option is called.
- **Why the review had to reach production** — the first review covered the development site alone: 1,223 options, one site. It produced a list that would have **leaked credentials on 32 of the 33 production sites**. Measured across all 33 (751 flagged rows): a license key on **32 sites**, 128–172 characters of base64; one plugin's access token (a 708-character JWT) and refresh token (1,504 characters); a second plugin's view secret; a third plugin's API key on 11 sites and its CDN token; a fourth plugin's stored credentials. None of those plugins exists on the development install, so no amount of care there would have found them.
- **Why bare suffixes** — the cause was structural, not a handful of oversights. Every pattern assumed `snake_case` (`%\_token`), so an entire naming convention passed through: of 58 undenied names, six used hyphens and two used camelCase, and **all eight were credential-bearing**. Dropping the separator from the pattern beats enumerating separators — `%token`, matched case-insensitively and anchored at the end, covers `some_token`, `some-access-token` and `someToken` in one reviewable line. Verified across all 751 rows: the bare suffixes catch every credential found and match nothing benign.
- **Why values are judged too** — a name-based denylist can only catch credentials someone already thought of, and the audit found the license key above **by its shape before any pattern named it**. The two halves fail in opposite directions and neither substitutes: names catch the empty credential that has no shape (the API key above is empty on ten of its eleven sites), shapes catch the credential whose name nobody predicted.
- **Rejected** — an allowlist, which reintroduces the enumeration problem the endpoint exists to avoid. And extending the patterns *without* the shape rule, which fixes the seven found and leaves the mechanism that produced them intact.
- **Consequences** — the payload reports withheld **counts split by reason** (`by_name`, `by_shape`) and never names. The split matters: a name match is a reviewed decision, a shape match is a guess about an option nobody enumerated, and an unexpected `by_shape` is the signal to look. On the current network the shape rule's entire collateral is **25 integrity hashes an import plugin stores** — it withholds nothing else, so today it is paying for itself prospectively rather than presently. `%key` is the pattern worth watching: a future option named `…monkey` would be withheld, which is the accepted direction.
- **Confirmed, not assumed** — the license key's status option is 273 characters on 32 sites and reads alarming. A query comparing it against the key with `INSTR` showed it is a serialized status array that does **not** contain the key, so it is served. Status and version fields generally are served; withholding them would drop configuration for no gain, which is the failure the first review committed with `%_keys` and `%user_roles`.
- **Pinned to a plugin set, not to a date.** A denylist is only as current as the plugins it was checked against, and "re-run the audit periodically" is not a control — it depends on somebody noticing a change that happened on another machine. So `config/defaults.php` records `option_denylist_reviewed_against` as a sorted list of plugin slugs, and the options payload reports `denylist: {reviewed_against, current, stale, added, removed}` for the site being read. Two `get_option` calls, at the only moment anything holds both the denylist and the plugin set at once.
    - **A subset test, not equality.** Every site in a network activates its own plugin set, so the baseline is the **union** across the network — and no individual site ever equals a union. Requiring an exact match would report `stale` on all 33 sites forever, which is a signal nobody reads. What matters is whether a site runs anything the denylist has never been checked against; a baseline entry the site does not run is another site's plugin, not a risk. It is reported as `removed` for the next refresh without making the payload suspect.
    - **Slugs, not a hash** — a hash says *that* something changed; a sorted list shows *what*, in the commit diff.
    - **Slugs, not slug+version** — versions would change on every routine update and train everyone to ignore the field. The accepted gap is a plugin introducing a new option name in a new version, which is what the value-shape rule is for.
    - **Reports, never refuses.** Refusing would make the signal undeniable and would turn a plugin activation on any of 33 sites into a halted migration. The hard check belongs in the consumer, which knows whether a call is a scratch query or the production pull; tracked against the importer.
    - **Empty means never pinned**, and that is today's honest state: the audit covered production's *options*, and nobody has captured production's *active-plugin list*. It reads `stale` until that is filled in from production — not from a development install, which would record the wrong thing and read as reassurance.
- **Network options are guarded by a test, not by this sentence.** `nonce_key` and `nonce_salt` are real secrets and live in `sitemeta`, which a per-site endpoint never reads — which is why the `%salt` pattern matches nothing. Serving a network option without revisiting this decision would ship them. Unlike a plugin arriving on production, that is a change *in this repository*, so `tests/Unit/NetworkOptionGuardTest.php` allowlists the network options `includes/` may read and fails naming the file and the option otherwise. An allowlist rather than a ban, because the plugin legitimately reads `active_sitewide_plugins` for the pinning above; a ban would have blocked that and taught the next person to route around the guard.
- **Ref** — #6, #12

### D-033 — The denylist looks inside a value, and the ACF view is filtered by it too

- **Decided** — `OptionsPayload` decodes a serialized or JSON option value and applies the shape rule to **every string inside it**, withholding the whole option on a match; a shorter, separately reviewed list (`option_denylist_nested_keys`) is applied to the **keys** inside a value; Google's `ya29.` and `1//` token prefixes join the vendor list; and the `acf` block of the payload is filtered by the same rules as the flat map.
- **Why** — D-032 judged a value as the string `wp_options` stored, and described the narrowness as a feature: "a PHP-serialized value carries `:` and `"` and never matches". That is true, and it was the hole. A settings row is one option holding a whole configuration, so the credential is a key several levels down. Verified by running the shipped methods: an identical SendGrid key was withheld as a bare value and served one level inside a serialized array. On the development install `geot_settings` was serving `api_secret` (65 bytes) and `license` (60 bytes) today; `wp-mail-smtp-pro`, `uamswp-seopress-pro` and `gravityformsgoogleanalytics` store credentials the same way and are all in production's active set.
- **Why the shape rule recurses and the name rule barely does** — measured against all 1,223 options here, applied to nested leaves: the shape rule found 3 leaves in 2 options, 2 of them real credentials; the full name list found 24 in 10, almost all noise. `%key` alone produced 22 — FacetWP's `templates.12.query_obj.orderby.0.key` is a sort column. A top-level option named `…key` is somebody naming a credential; a *key* named `key` is just a key. So the nested list drops `%key` and `%password%`, and fires only on a **non-empty string**: keyed on the name alone it also withheld `wp_user_roles.administrator.capabilities.seopress_manage_license`, a capability whose value is boolean `true`, taking all 22 KB of the network's role definitions with it — the same false positive D-032 already paid for once with `%user_roles`.
- **Why the ACF block had to be filtered** — `acf_get_value( 'options', $field )` resolves to `get_option( "options_{$name}" )`, so every value the flat map withheld was read straight back out and served in full one key later. The same response reported a withholding that had not happened, beside a dangling `_options_*` reference pointing at an absent value. A denied field now leaves **both** ACF maps: they are keyed by field key and by field name, so removing it from one alone ships it under the other spelling — which is why `FieldReader::read()` now returns the pairing.
- **Rejected** — redacting the offending leaf rather than withholding the option. It mutates the value, which breaks raw-not-curated (D-004), and the denylist withholds whole rows everywhere else. Also rejected: exempting ACF options-page rows from the name rule instead of filtering the ACF view, which would have widened what the flat map serves to fix an inconsistency in what the structured view serves.
- **Consequences** — 4 more of this install's 1,209 served options are withheld: `geot_settings`, `PMXE_Plugin_Options` and `_asp_media_service_data` carry real credentials, and `fs_accounts` carries a Freemius install ID that is not a secret. That last one is real data loss in the accepted direction, and it is visible in the `by_shape` count. Decoding is for **inspection only** — what ships is unchanged, so a JSON string still goes out as the string it is (D-009). It decodes with `allowed_classes: false`, because inspecting a value nobody has audited must not be able to construct anything and run its `__wakeup()`; `tests/Support/WakeupProbe.php` gives a real class a visible side effect and the suite asserts it never fires. The walk is depth-bounded at 16 and **fails closed**, because `R:` back-references let a value contain itself.
- **The audit script calls the endpoint rather than transcribing it.** `OptionsPayload::classify()` and `matchesLikePattern()` are public for exactly one caller, `scripts/audit-option-denylist.php`, and that is a deliberate trade of encapsulation for the impossibility of drift. The script had kept its own copy of the rules under a docblock reading *the audit has to classify exactly as the endpoint filters, or it reports on a denylist nobody ships* — and then this decision landed, the copy did not follow, and for a release the one tool for reviewing the denylist against production reported on a denylist that was not shipped (#38). What the script keeps is the **opposite** question: heuristics for what the endpoint might be *missing*, deliberately looser than the shipped rule, run over the rows that are served. Tuned against this network rather than guessed — the first draft reported 92 candidates, 75 of them FacetWP field references, and a detector nobody reads is worth less than none; requiring mixed case and a digit for an opaque run, and no whitespace for a name match, took it to 8.
- **Ref** — #33, #31

### D-034 — Registration-scoped endpoints refuse a cross-site request rather than serve a mixed one

- **Decided** — `GET /post-types` and `GET /taxonomies` return **400** when `?site=` points at any site other than the one that booted the request. `GET /sites` is unaffected and reports every site.
- **Why** — post-type and taxonomy registration is **process-global**, not per-site. Plugins register on `init` for whichever site handled the request, and `switch_to_blog()` does not re-run that. Measured: 16 types registered before a switch and 16 after, and a type registered *while* switched is still registered once restored. What a switch does change is anything read from the database — options and counts.
- **So the failure mode was specific** — serving `?site=N` would have returned the booted site's **registrations** beside site N's **counts**: a well-formed response describing two different sites at once, which is this project's defining failure. Every endpoint inherits site scoping from `Site::switchForRequest()`, and this is the one place where inheriting it silently produces nonsense.
- **Rejected** — reporting both `registered_for_site` and `counted_for_site` so a consumer could detect the mixture. It is honest, and it makes correctness the consumer's problem for a case with an easy right answer: the namespace is registered on **every** site in the network, so the way to ask site N what it registers is to ask site N.
- **Consequences** — `Site::isSwitched()` exists for this. `get_current_blog_id()` cannot answer the question: the switch happens on `rest_pre_dispatch`, so by the time a handler runs the current blog already *is* the requested one and any comparison against it is always false.
- **Observed from outside the process**, which is stronger than the internal measurement above. Taken by the `wordpress-importer` side against the development network — same install, same credential, same minute:

  | Request | Result |
  | --- | --- |
  | `…/wp-json/uamswp-migration/v1/post-types?site=1` (site 1 serves) | `200` — 36 records, **14** flagged `exposed` |
  | `…/wp-json/uamswp-migration/v1/post-types?site=2` | `400 uamswp_migration_api_registration_is_not_site_scoped` |
  | `…/wp-json/uamswp-migration/v1/post-types?site=3` | `400`, same |
  | `…/scoping-two/wp-json/uamswp-migration/v1/post-types` (site 2's **own** REST root) | `200`, **13** flagged `exposed` |

  > The figures above are as measured on 2026-08-19. `logo-list-item` was added to the exposed set on 2026-08-21 (D-052), so the same request now reports **15** exposed rather than 14. The example is left at its measured values rather than re-written, because the point it makes is about denominators, not about the current count.

  **Read the counts carefully — the endpoint does not return 14.** `GET /post-types` reports *every* registered type, each carrying an `exposed` boolean; on site 1 that is **36 records of which 14 are exposed**, and 14 is also what `exposed.post_types` reports on the namespace index. The reporting side wrote "14 exposed post types", which is the right number attached to the wrong denominator, and re-running it here is what surfaced that. Worth preserving as written: a number that is correct and still misleading is the harder kind to catch.

  **The 14-against-13 is the whole point.** It is not an assertion that registration is process-global — it is a number that could only differ if it were, produced by asking two sites the same question two different ways. Recorded here rather than left in the bug ticket it surfaced in, because that ticket is about a client passing `?site=` it should not have; someone looking for *how site scoping behaves* would never find it there.
- **The error text is load-bearing, and that is now confirmed rather than hoped.** D-041 argues an error should name the thing that is missing and the way out. The consumer that hit this one reports never opening a ticket, never reading this file, and never looking at the source: the message said to ask site N through its own REST root, they tried exactly that, it returned `200`, and the diagnosis took one command. The cost of writing the fix into the message is paid once, here.
- **Ref** — #3, #12

### D-035 — The WXR channel header is reproduced function for function, not in spirit

- **Decided** — `GET /sites` fills `title`, `link`, `description` and `language` from `get_bloginfo_rss()`, `base_blog_url` from `get_bloginfo_rss( 'url' )`, `base_site_url` by `wxr_site_url()`'s rule, and `wxr_version` by reading `WXR_VERSION` out of `wp-admin/includes/export.php`.
- **Why** — the importer's `XmlParser::getBaseBlogUrl()` returns `wp:base_blog_url` verbatim and uses it for URL rewriting and internal-link resolution, so the contract is byte-identity rather than equivalence. `get_bloginfo_rss()` is not `home_url()`: it applies `strip_tags()`, `convert_chars()` and the `get_bloginfo_rss` filter, so the two diverge on any site that filters them. A near-miss here produces links that resolve but are wrong.
- **`base_site_url` and `base_blog_url` are not interchangeable** — measured on this network, `network_home_url()` returns `http://…/` where `get_bloginfo_rss( 'url' )` returns `https://…`: different scheme *and* trailing slash.
- **Rejected** — hardcoding `1.2` for the WXR version. It becomes wrong the day core bumps it and tells the importer the wrong format version. The constant is **parsed** out of core rather than required, because that file is an admin include defining `export_wp()` and two dozen helpers, and a REST request has no business loading it for one constant. Unreadable yields `null`, which is honest where a guess would be indistinguishable from a fact.
- **Ref** — #3

### D-036 — `/sites` reports three post figures, because one was misleading

- **Decided** — `counts` carries `rows` (the whole `wp_posts` table bar `auto-draft`), `posts` (only the post types `config/defaults.php` lists) and `by_post_type` (the full breakdown). `terms`, `comments` and `options` stay single whole-table figures.
- **Why** — `posts` used to be the unfiltered row count, and on the development install that is 1,453 against 462 configured: a **3.1x overstatement, two thirds of it revisions**, plus post types outside `config/defaults.php`. A consumer sizing a migration, or reconciling a finished one, was working from a number several times the real one. Production is worse, because revision counts scale with editing history and `uamshealth.com` is the site whose history already defeats core’s exporter.
- **The argument was already in the code** — the original `auto-draft` exclusion was justified as "counting them would inflate every planning figure the importer works from". A revision inflates it identically; so does a type this deployment does not serve. The rule was right and was applied to one case out of three.
- **Why additive rather than a redefinition** — dropping the unfiltered figure would lose a fact that is cheap and honest to report (D-004), and `by_post_type` is what turns the endpoint from something you plan a run with into something you can verify one against. It also surfaces a type present in the table but **not registered** in this process — 28 `kb` rows here, plus 6 `uamspeople` — which `GET /posts/kb` answers with a 404 and nothing else reports. `by_post_type` is a table inventory rather than a fetch plan: it lists `revision` and `acf-field` too. The registration signal lives where D-034 put it, on `/post-types`, which refuses a cross-site request in order to answer it honestly and flags each type `exposed`.
- **Rejected** — keeping `posts` as the whole-table count and adding only a breakdown. The misleading name was the defect; leaving it in place and documenting the correction elsewhere is how a payload accumulates traps.
- **Eligibility comes from configuration, not from `post_type_exists()`** — and that distinction is D-034 applied to a place it had not been. Filtering the breakdown with `Config::allowsPostType()` judged site N's rows against the **booting** site's registrations, because registration is process-global and a switch does not re-run it. D-034 named `/sites` as unaffected by that; this would have made it the one endpoint that was. The production consequence is silent under-reporting: Find-a-Doc registers `provider`, so a request booted on a site without it would have reported zero providers for the thirty sites that have them. The configured list is a deployment-level fact, identical for every site, so it mixes nothing — and what a given site can actually register stays the business of `/post-types`, which refuses a cross-site request in order to answer it honestly.
- **Consequences** — `counts.posts` changes meaning for any consumer already reading it. Nothing does yet, which is why this landed before the importer began consuming `/sites` rather than after. `posts` may now count rows of a type this process has not registered; that is deliberate, and `by_post_type` beside it is what lets a consumer see the difference.
- **Ref** — #36, #3, #41

### D-037 — Terms are a resource, and `hide_empty` is off

- **Decided** — `GET /terms/<taxonomy>` and `/terms/<taxonomy>/<id>`, paginated by `term_id` ascending, carrying raw termmeta with underscore-prefixed keys, ACF's assembled view, and both `term_id` and `term_taxonomy_id`. `get_terms()` is called with `hide_empty => false`, and the total header is counted the same way.
- **Why a resource rather than a sub-resource** — a term reached only through the post that references it arrives with a name and nothing else. WXR carries `wp:termmeta` in 103 of the 259 captured exports, so this is parity work, and Find-a-Doc hangs ACF field groups on thirteen taxonomies whose values live nowhere in a post payload.
- **`hide_empty => false` is the load-bearing line.** `get_terms()` hides terms with no assigned posts unless told otherwise, so the WordPress default would silently drop every unused term from a migration — the taxonomy arriving at the destination missing exactly the terms nobody had used yet, with no error anywhere. The count header uses the same rule, because a total that disagrees with the page beside it fails in the direction of a consumer believing it had finished.
- **No `modified_after`** — `wp_terms` and `wp_term_taxonomy` carry no date column, so there is nothing to filter on, and a parameter that silently matched everything would be worse than its absence. A full re-pull of terms is cheap: this network's largest taxonomy is three orders of magnitude smaller than its post table.
- **`term_taxonomy_id` beside `term_id`** — they are different numbers and WXR's `wp:term_id` is ambiguous about which it means. The relationship table keys on the former, so an importer rebuilding assignments needs it.
- **Consequences** — `Pagination` gained no term-shaped helper. The stubs seal `get_terms()`' argument shape, so its arguments are built at the call site while `Pagination` keeps the bounds; the ordering rule is stated there in a comment rather than centralized, which is the cost of the sealed shape. The three request-narrowing helpers moved from `PostsController` to the base `Controller`, because two controllers needing them was the moment a copy would have started drifting.
- **`parent_slug` beside `parent`** — every WXR taxonomy shape carries the parent *slug*, not its id: core writes `$terms[$t->parent]->slug` for `wp:term_parent` and the same for `wp:category_parent`. An id is not derivable back to a slug without the whole taxonomy in hand, and ids do not survive a migration — the argument that makes the term's own slug load-bearing applies to its parent unchanged.
- **The collection re-resolves each row against the route's taxonomy.** `WP_Term_Query::populate_terms()` calls `get_term( $id )` with no taxonomy and `_prime_term_caches()` keys the cache by `term_id` alone, so a term existing in two taxonomies can be served from the other one's cached row — the collection disagreeing with the single endpoint, which does pass the taxonomy. Not reachable here (WordPress 4.4 stopped creating shared terms, 4.3's splitter cleared the legacy ones, and this install reports zero with `finished_splitting_shared_terms = 1`), and the 33 production databases were not inspected. One line that makes the two endpoints agree by construction was cheaper than finding out.
- **Resolved in D-038: the `acf` view used to carry field defaults as though they were stored values.** `acf_get_value()` substitutes `default_value` when no meta row exists, and on this install that is 16,626 of 45,249 term fields — 37%, almost all on `clinical_title`. That contradicts D-004 and it is not introduced here: the mechanism is in `FieldReader` and posts have it too. Split into its own map rather than suppressed, so both facts survive — see D-038.
- **Ref** — #5, #43, #45

### D-038 — Stored ACF values and values the definition supplied are separate maps

- **Decided** — `acf` carries `keys` and `names` for values the row actually holds, and a sibling `defaulted` block carrying `keys` and `names` for values `acf_get_value()` substituted out of the field definition. Neither map mixes the two. `FieldReader` gains a fifth allowed ACF function, `acf_get_metadata_by_field()`, to tell them apart.
- **Why** — `acf_get_value()` ends with a substitution of `$field['default_value']` whenever the stored value is null, and it does that **before** the `acf/load_value` filter, so nothing downstream can distinguish a stored value from a manufactured one. Measured before the split: **16,626 of 45,249 term fields** and 8% of sampled post fields were served carrying a value no row held. `field_certificate_url_query` is the shape of it — a `button_group` with `default_value: 1`, served as `1` for terms nobody had touched, so an importer writes an affirmative flag the source never held.
- **Why split rather than suppress** — a default is genuinely what ACF returns to a rendering page, so a consumer replicating behavior wants it; dropping it is lossy in the opposite direction. And this is D-005's argument one level down: the raw fact is *no row*, the composed fact is *ACF would say 1*, and the API reports both and composes neither. Suppressing would also make absence ambiguous between "no row" and "no such field".
- **Rejected** — flagging inline with a list of defaulted keys beside the mixed map. It breaks no existing reader, and it leaves `acf` meaning two things at once, which was the defect rather than a mitigation of it. Also rejected: documenting the behavior and changing nothing, which does not carry the bit a consumer needs.
- **Why a fifth ACF function** — `acf_get_metadata_by_field()` is the only clean signal, returning null when no row exists, and it is what ACF Custom Database Tables intercepts through `acf/pre_load_metadata`. That last part is load-bearing: a plain `get_post_meta()` check would report "no stored row" for exactly the `location` and `provider` values that live only in custom tables, which is the staleness this whole project exists to route around. `tests/Unit/AcfApiGuardTest.php` widens from four functions to five, which is the guard working — it exists to make an addition an argued decision.
- **Three cases, and two of them were wrong first** — both caught by tests rather than by reading. A **container** has no row of its own: a `group` stores nothing and its children do, so `acf_get_metadata_by_field()` returns null for a fully populated group and the first draft moved every group and repeater into the defaulted map. Detected by shape rather than type, per D-031. And an **empty default is not a supplied value**: `acf_get_valid_field()` gives most types `default_value => ''`, so without that rule every unset text field would land in the defaulted map carrying an empty string.
- **Consequences** — on this install the split moves **13,092 term field values** into `defaulted` against 21,114 stored, almost all of the former on `clinical_title`. A consumer reading `acf.keys` today sees fields move; nothing consumes it yet, which is why this landed now. The count is lower than the 16,626 first measured because the container and empty-default rules correctly reclassified roughly 3,500 of them.
- **Residual** — `default_value` can itself be filtered at load time, so "the definition's default" means whatever ACF computed on that request. A stored value that happens to equal the default is indistinguishable by value, which is what the split is for. And the custom-table awareness is verified here, where ACF CDT is inert; on production it is live, so it wants one confirmation against a site where `has_table()` actually fires.
- **Ref** — #45, #5, #4

### D-039 — Attachments carry the file URL, and the decoded metadata beside the raw row

- **Decided** — an `attachment` block on attachment records only, carrying `url`, `mime_type`, `file`, `alt` and a decoded `metadata`. Null on every other post type. The flat `meta` map is unchanged and still carries `_wp_attachment_metadata` as the serialized string.
- **Why `url` is not optional** — it is the one item-level WXR element nothing else here carried, and the two fields that look like substitutes are not. `guid` reads like a file URL and is an opaque identifier: WordPress documents it as such, it is stored with whatever scheme the row was written under (`http://` across this network, against `https://` sites), and core emits it *separately* from `wp:attachment_url` for that reason. `link` is the attachment page permalink. Only `wp_get_attachment_url()` resolves the file, which is what core calls at export.php:651 and therefore what parity means.
- **Why the metadata is decoded here and serialized there** — D-005 again. `wp:postmeta` carries the serialized string byte for byte and an existing importer already decodes it, so `meta` keeps it; the `sizes` map is where an asset importer finds every derivative it must fetch, so the assembled shape saves the common case from parsing a string this API had already parsed. Both ship.
- **`mime_type` is a superset, not parity** — WXR carries no mime type. It is on the post row, and an asset importer needs it to know what it is fetching before it fetches.
- **Consequences** — 2,011 attachment records across the 259 captured exports gain a resolvable URL. `_thumbnail_id` on parent posts already survived through the raw-meta rule (D-007) and is now asserted rather than assumed.
- **The test that nearly did not test anything** — asserting `url` equals `wp_get_attachment_url()` passed against an implementation serving `$post->guid`, because on a freshly created attachment the two are identical. The test now moves the guid off the file first, which requires writing the row directly: `wp_update_post()` silently ignores `guid`, since core sets it only on insert. Both facts were found by mutation, not by reading.
- **Ref** — #8

### D-040 — `GET /authors` serves the email, and comments are out of scope

- **Decided** — `GET /authors` covers WXR's `wp:author` block in full, email included, plus the nicename. Comments and comment meta are **not** served: #10 ships authors only.
- **Which users** — those referenced as a post author, which is core's own rule: `wxr_authors_list()` selects `DISTINCT post_author` from `wp_posts` excluding `auto-draft`, then resolves each. On a multisite network with one shared user table that distinction is load-bearing — it is the difference between the handful of people who wrote a site's content and everyone who has ever logged in to any of the 33 sites.
- **Why the email ships** — it is personal data, and the argument for withholding it does not survive contact with where that data already is: **2,090 author blocks carrying emails sit in the 259 exported XML files**, in the importer's captured corpus. Withholding it from an authenticated API that already serves unpublished content and raw site settings protects nothing while risking attribution across the **861 distinct author logins** in that corpus. Omitting it would also break the strict-superset claim (`wordpress-importer#588`) on a block WXR carries in full, and would degrade attribution *silently*, which is this project's defining failure.
- **Rejected** — omitting the email, and gating it behind a flag. The flag is the worse of the two: a run that silently went without it would produce wrong attribution and no error.
- **Why comments are out of scope** — a decision taken with the data in hand rather than by default. The survey found comments are **not** absent: 1,023 across 44 of the 259 exports, 955 of them real (the rest pingbacks and trackbacks), with 674 commentmeta rows. So the issue's own "close it if a survey finds nothing" condition was **not** met. They are excluded anyway, on the call that they have nowhere to land at the destination. Recorded as a scope decision rather than a survey finding, because the two are different and only one of them is true.
- **What the survey also showed, worth keeping** — every commentmeta key is machinery rather than content: `_wxr_import_user` (295), `akismet_history` (130), `_wp_trash_meta_*` (82 each), `akismet_result` (67), `antispam_bee_iphash` (11). The first of those is an artifact of a **previous WXR import**, so parts of this corpus have already been through one migration — worth knowing before treating it as pristine source.
- **Consequences** — an author whose user row has been deleted is dropped, because `get_userdata()` returns false and core's `array_filter()` does the same. The two agree, and neither reports the loss; reporting it is #50.
- **Ref** — #10, #50, `wordpress-importer#588`
- **Amended by D-047** — the silent drop this recorded as accepted is no longer silent; `GET /authors` reports orphaned author ids.

### D-041 — A type this deployment serves but this process has not registered gets its own error

- **Decided** — `GET /posts/<type>` and `GET /terms/<taxonomy>` keep accepting `?site=`, and split their 404 in two. A name absent from `config/defaults.php` stays `uamswp_migration_api_unknown_post_type` / `…_unknown_taxonomy`. A name the deployment **does** serve but this process has not registered returns `…_type_not_registered_here` / `…_taxonomy_not_registered_here`, naming the site to ask instead when the request carried `?site=`.
- **Why this is only about the error** — a cross-site request for a type only the target site registers **cannot be made to work.** Registration runs on `init` for whichever site booted the request and `switch_to_blog()` does not re-run it (D-034); nothing re-runs another site's plugin set inside one process. So the choice was never how to support it, only how it fails — which made this a diagnostics decision rather than an architectural one.
- **What was actually wrong** — not the 404 but its content. "That post type is not served here" is false for a type the deployment is configured to serve, and it sends a consumer to check its own configuration when the fix is to re-issue against a different REST root. On this install `kb` (28 rows) and `uamspeople` (6) are exactly that case.
- **Rejected: serving it anyway, and this was measured rather than assumed.** `WP_Query` does return the rows — but `get_object_taxonomies()` yields nothing for an unregistered type and no ACF location rule matches it, so the record arrives with an **empty `terms` block, zero ACF values and a `?p=` fallback permalink**. A well-formed 200 missing half the record is strictly worse than a loud 404, and it is this project's defining failure mode.
- **Rejected: refusing every cross-site request**, the way D-034 does for `/post-types`. It is more consistent and it removes a case that genuinely works — `post`, `page` and `attachment` are registered on every site, so cross-site paging for core types works today. Breaking the majority case to make the minority fail earlier is the wrong trade when both already fail loudly.
- **The residual inconsistency, stated rather than hidden** — `/post-types` refuses `?site=` while `/posts/<type>` accepts it. That is deliberate: they answer different questions. `/post-types` *is* a question about registration, so a cross-site answer would be nonsense; `/posts/<type>` is a question about content, and registration is only a precondition it can now report on precisely.
- **Both controllers, one change** — a decision applied to one of two is how they drift, which is what #38 was about.
- **The residual, and it was chosen rather than missed** — `/post-types` and `/taxonomies` list what is *registered*, so a configured-but-unregistered name does not appear there at all. On this install that is `kb` (28 rows) and `uamspeople` (6): `GET /posts/kb` now states precisely why it cannot serve them, and nothing in discovery reveals they exist. Reporting them there was offered and declined, on the grounds that it adds payload and surface to warn about a case whose error is now self-explanatory. A consumer that walks `/sites` per site — the access pattern D-034 already prescribes — never meets the case at all.
- **Consequences** — `Config::allowsPostType()` and `allowsTaxonomy()` are no longer used by the gates, because they fold registration into the configured check and so cannot tell the two failures apart. The gates read the configured list directly, as `counts()` does since D-036.
- **Ref** — #43, D-034, D-036

### D-042 — Channel `title` and `description` are decoded; the URLs are not

- **Decided** — `GET /sites` serves `title` and `description` through `html_entity_decode()`, and leaves `link`, `base_blog_url` and `base_site_url` exactly as `get_bloginfo_rss()` returns them.
- **Why** — "function for function" (D-035) was one function short. Core writes the channel header with `bloginfo_rss()`, which applies one filter more than `get_bloginfo_rss()`, and core registers `ent2ncr` on it (`default-filters.php:268`) — rewriting `&amp;` as `&#38;` for the XML parser to turn back into `&`. So a site named `Ear, Nose & Throat` reached a WXR consumer decoded and reached this payload encoded, and the two paths disagreed on any site whose name contains an ampersand.

- **Why only those two** — `base_blog_url` is the one channel field with a live consumer: `XmlParser::getBaseBlogUrl()` is used verbatim for URL rewriting in at least five places in the importer. A URL carries no entities to decode, so touching it would risk the field that matters to fix two that, verified against the importer source, **nothing reads at all** — `XmlParser` exposes no getter for channel title or description.

### D-043 — Both of `GFAPI`'s two default filters are overridden, in opposite directions

- **Decided** — `GET /forms/gravity` calls `GFAPI::get_forms(null, false, 'id', 'ASC')`, widening `$active` to include inactive forms and keeping `$trash` narrow. `GET /forms/gravity/<id>` re-checks the trash flag itself and 404s on a trashed form.
- **Why the widening** — `GFAPI::get_forms()` is declared `$active = true`, so the call everyone writes returns only *active* forms. A form somebody switched off is content the destination may still need, exactly as an unused taxonomy term is (D-037), and the omission arrives as a 200 with no error anywhere. `GFFormsModel::get_form_ids()` skips the filter entirely when the argument is `null` — `if ( null !== $active )` — which is the only way to get both classes in one call.
- **Why the narrowing stays** — trash is WordPress' delete. D-004's "raw, not curated" governs how a record is *shaped*, not whether a deleted one is resurrected.
- **Why `show()` needs its own check** — the plugin's two readers disagree about trash, and in the direction that leaks. The collection filters `is_trash = 0` in SQL, while `GFAPI::get_form()` calls `GFFormsModel::get_form( $id, true )`, whose second argument is `$allow_trash`. Left alone the endpoint withholds a trashed form from the page and serves the identical form on its own route — the narrower route being the one that resurrects a delete. The flag arrives as the string `'1'`, so the check is a loose truth test; `=== true` would pass every trashed form through.
- **Why no payload class** — `GFAPI::get_form()` already returns the whole definition, and the 161 committed fixtures are that shape. `GFAPI::get_forms()` is a loop over `GFAPI::get_form()`, so the two routes share a shape by construction rather than by agreement; a pass-through class would be ceremony. Asserted anyway, because that is a plugin-internal detail this repo does not control.
- **The payload carries `GF_Field` objects, not arrays** — `GFAPI` returns each field as a `GF_Field` subclass, so the records are objects nested in arrays. They encode correctly (every public property reaches the JSON: `type`, `label`, `isRequired`, `choices`, `conditionalLogic`), so nothing converts them. The consequence is for tests, not consumers: comparing `get_data()` against a decoded fixture compares objects with arrays. `GravityFormsFixtureParityTest` round-trips through `wp_json_encode()` and asserts the wire shape, which is the only shape the importer ever sees.
- **Fixture parity is asserted against the real corpus, not a vendored copy** — `UAMSWP_MIGRATION_API_TESTS_GF_FIXTURES` points at the importer's `Tests/Exports/GravityForms`, and the test skips when it is unset. Those exports are production form definitions carrying real notification recipients, so they are not committed here; notifications and confirmations are compared by md5 digest so a failure cannot print a recipient into a log. Gravity Forms re-keys notifications by their own `id` on import, so the comparison is by value rather than by array key — the content is byte-identical, the indexing is not.
- **Definitions only** — entries are deferred to #54, not dismissed. `wp_gf_entry` holds submitted data for a health system and the importer references no entry API anywhere, verified against its source.
- **Ref** — #11, #54, D-004, D-037

### D-044 — Gravity Forms is a fourth optional plugin in the test bootstrap

Tests needing a real `GFAPI` skip without it; `tests/Feature/Forms/GravityFormsGuardTest.php` reds a run that had it on disk and failed to load it.

### D-045 — A collection primes its records' parents, and runs with query filters suppressed

- **Decided** — `PostsController::index()` calls `_prime_post_caches()` over the page's distinct `post_parent` ids before building payloads, and `queryArgs()` sets `suppress_filters => true`.
- **Measured, on the development install, with the same harness before and after** (a real dispatched request, `SAVEQUERIES` on, 27 attachments):

  | records | before | after |
  | ---: | ---: | ---: |
  | 1 | 48 | 46 |
  | 5 | 50 | 48 |
  | 10 | 58 | 48 |
  | 27 | 77 | 48 |

  Before, cost grew about 1.2 queries per record; after it is flat. The payload is byte-identical either way — same 176,999 bytes, same md5 — so this bought cost, not a different answer.
- **Why priming** — `WP_Query` primes the caches for the ids it returned and knows nothing about what those rows point at. `PostPayload` then reads each record's parent, because `get_permalink()` on an attachment resolves its parent to build the URL, and every one of those was a cache miss: a `SELECT * FROM wp_posts WHERE ID = N` and a single-id postmeta prime per record — 15 of each for 27 attachments. One batched call collapses both to one query each. The scale is the argument: attachments are the highest-volume type in the captured exports, 2,011 of them, more than every other type combined, and this API paginates precisely because `uamshealth.com` cannot complete a single-request export.
- **Why `suppress_filters` is a correctness setting first** — it gates the `posts_*` clause filters, and each is a plugin's opportunity to rewrite what a query returns, which is what D-004's "raw, not curated" forbids. On this network the one that matters is GeoTargeting WP: it hooks `posts_where` at `PHP_INT_MAX` to *remove posts from the loop* based on where it believes the visitor is. A migration read that silently omits records is this repo's defining failure mode.
- **Enumerated rather than assumed** — the eight callbacks suppressed on the development install are geo exclusion (`GeotWP_Public::handle_geotargeted_posts`), three search rewrites (Ajax Search Pro, Relevanssi, TablePress), two ACF admin-query filters, and core's `_close_comments_for_old_posts`. None is something a migration read wants; the search ones cannot fire on a query that passes no `s`; and core's early-returns unless `is_singular()`. `tests/Feature/RawQueryTest.php` registers a `posts_where` filter of exactly GeoTargeting's shape and asserts the excluded post is still served, and that `X-WP-Total` still agrees with the records.
- **Not total protection, stated so nobody assumes it is** — and the gap is wider than this entry first recorded. `pre_get_posts` is an *action*, not one of these filters, and still runs. **`posts_pre_query` also still runs**: it is a filter, but core applies it *outside* the suppression branch — `class-wp-query.php` closes `if ( ! $q['suppress_filters'] )` at line 3209 and fires `posts_pre_query` at 3227 (verified against the 6.8.8 install, 2026-08-21). It short-circuits the query and returns a result set of the callback's choosing, so it is the stronger of the two holes, not a footnote to the first. A plugin determined to alter a migration read can still do so from either.
- **The `geot_*` queries are explained, not eliminated** — 36 of the 39 came from ACF's page-template location rule: `FieldReader` → `acf_match_location_rule` → `ACF_Location_Page_Template::match` → `acf_get_post_templates()` → `get_block_templates()`, which constructs a `WP_Query`, which fires GeoTargeting's filter. GeoTargeting re-runs its query every time because its cache only populates on a non-empty result (`if ( ! empty( self::$_geotarget_posts ) )`), and this install has zero geotargeted posts. It is a third-party defect reached through another third-party plugin, and it is **fixed overhead per request rather than per record** — which is why the after-column is flat. Deactivating GeoTargeting WP, which this network reportedly does not use, would remove it; that is an install decision, not a code one.
- **What was not measured** — a page of 100. The development install holds 27 attachments, so the flat line is demonstrated to 27 and projected beyond it. Production, where the plugin set is larger and the attachment count is two orders of magnitude bigger, is still unmeasured — #12 territory.
- **Ref** — #49, #8, #48, D-004

### D-046 — Formidable is read with `FrmForm::getAll()`, never `get_published_forms()`, and trash is filtered in PHP

- **Decided** — `GET /forms/formidable` reads `FrmForm::getAll(['id >' => 0], 'id', '')` and drops trashed rows in PHP; `GET /forms/formidable/<id>` re-checks the trash flag itself; fields come from `FrmField::get_all_for_form($id, '', 'include', 'exclude')`.
- **Why not the obvious call** — `FrmForm::get_published_forms( $query = array(), $limit = 999, $inc_children = 'exclude' )` drops data three separate ways, each silently and each with a 200:
  - `$inc_children = 'exclude'` hides every child form. Formidable Pro stores a repeating section or an embedded form as a **separate row** pointing at its parent, and **11 of the 68 forms in the importer's 12 committed exports are children** — 16% of the corpus.
  - `$limit = 999` is a cap nobody asked for.
  - The query pins `status` to `array( null, '', 'published' )`, so a **draft** form vanishes — content the destination may still need, the same argument that keeps inactive Gravity forms (D-043) and unused taxonomy terms (D-037).

  It also orders by `name`, where every collection here orders by id ascending so a page boundary means the same thing twice (D-006).
- **Why trash is filtered in PHP rather than SQL** — `getAll(['status !' => 'trash'])` compiles to `status != 'trash'`, and **SQL inequality never matches NULL**, so it silently drops every row whose `status` column is NULL. Verified against a real NULL row: the SQL form returned `[1,2]` where the PHP filter returned `[1,2,3]`.
- **Why `$limit` is `''` and not `0`** — `FrmDb::esc_limit( 0 )` produces a literal `LIMIT 0` and returns **nothing at all**. Verified, and it is the kind of mistake that reads as "this site has no forms".
- **Why `show()` re-checks trash** — `FrmForm::getOne()` applies no status filter whatever; it fetches by id and returns a trashed form exactly as it returns a live one. The same asymmetry Gravity Forms has (D-043), in the same leaking direction: without the check the narrower route serves what the collection withheld.
- **Why fields widen `$inc_embed`** — `FrmField::get_all_for_form( $form_id, $limit = '', $inc_embed = 'exclude', $inc_repeat = 'include' )` omits the fields of an embedded form by default. A definition carrying a form but not the fields inside the form it embeds is a definition with a hole in it, and nothing in the response says so.
- **Composed from two tables, not curated** — `frm_forms` and `frm_fields` are served together because a form definition without its fields is not one. Columns are handed over as the models return them; `options` and `field_options` are passed through in whatever shape the model gives, which is the only form that survives a field type this deployment has never heard of (the argument D-031 makes for ACF).
- **`form_key` is load-bearing** — ids are reassigned on import, the key is not, and it is what Formidable's own shortcodes and exporter reference. The fixture-parity test compares by key for exactly that reason. Same argument as a term's slug.
- **Definitions only** — `wp_frm_items` and `wp_frm_item_metas` hold submissions; #54 owns that question for both form systems.
- **Add-on scope, which #1 asked to confirm** — measured from the corpus rather than from the network's installed list: of 2,412 captured fields, ~23% are Pro-tier types (`divider`/`end_divider` 314, `date` 136, `address` 29, `file` 23, `break` 14, `rte` 8, and the long tail). **Formidable Pro is required; nothing else is.** `signature` appears **zero** times in 2,412 fields, so Digital Signatures is not needed; Views, User Tracking, Bootstrap and the GF Importer contribute no field types and no definition data, nor do the nine other add-ons on disk. One unknown remains: 8 fields use type `rcwdupload`, which belongs to no Formidable add-on.
- **Amended by D-081** — *definitions only* here draws the line against submissions, and form actions sit on the definitions side of it; they were not served, and D-081 decides they will be.
- **Ref** — #1, #54, D-004, D-006, D-030, D-031, D-037, D-043, D-044

### D-047 — `GET /authors` reports the authors it cannot resolve, and counts only the ones it can

- **Decided** — the collection partitions referenced author ids into resolvable and orphaned **before** paging. It serves the resolvable ones, sets `X-WP-Total` from that count, and reports the rest on two headers: `X-UAMSWP-Orphaned-Authors` (a count, always present) and `X-UAMSWP-Orphaned-Author-Ids` (the ids, capped at 200).
- **Measured before it was built**, which #50 asked for first. Across the importer's **259 captured exports**, restricted to the 16 post types this API serves:

  | | |
  | --- | ---: |
  | items | 216,197 |
  | with a resolvable author | 213,605 |
  | **with an author that does not resolve** | **2,592 (1.20%)** |
  | exports affected | 28 of 259 |

  Concentrated in attachments (1,598), but 397 `post` and 118 `page` items too. Small, real, and invisible without this.
- **What the corpus cannot say** — WXR emits an empty `<dc:creator>` both for a deleted author and for `post_author = 0`, because `get_the_author_meta( 'login' )` returns `''` either way. So 2,592 is an **upper bound** on true orphans, not a count of them. Stated rather than rounded off, because the distinction is not recoverable from the files.
- **What the survey ruled out** — the *named* orphan, an author login referenced by an `<item>` but absent from the file's `<wp:author>` blocks, occurs **zero** times in 216,564 non-empty references. The failure mode is entirely the unresolvable one.
- **Why the total changed too** — this was a second defect, found while fixing the first. `X-WP-Total` was built from the unfiltered id list while the records dropped orphans, so the total promised records no page could contain and a consumer paging to the end always came up short. Partitioning before slicing fixes both that and a page straddling an orphan, which used to return fewer records than `per_page` with nothing to say why — indistinguishable from the end of the collection.
- **Why two headers** — they answer different questions and the count stays true when the list is capped. The cap exists so a pathological site cannot push a header past what a proxy will carry; comparing the count against the listed ids is how truncation is detected, so it is never silent.
- **Why the ids are safe to serve** — they already appear in every post payload as `author`. Listing them reveals nothing a consumer paging `/posts` does not already hold, and an id alone is not personal data.

### D-052 — `modified_after` widens in every direction it was narrow, and never-published records are always served

- **Decided** — `PostsController` normalizes the caller's timestamp to GMT itself, floors a bare date to midnight, and OR's a second `date_query` clause that always matches never-published records. An unreadable timestamp is a `400` rather than an ignored filter.
- **Three defects, one parameter, all measured on the development install** (`gmt_offset = -5`, WordPress 6.8.8):

  | input | compiled to (before) | records lost |
  | --- | --- | --- |
  | `2026-08-01` | `> '2026-08-01 23:59:59'` | everything edited that day |
  | `2026-08-01T12:00:00+00:00` | `> '2026-08-01 07:00:00'` | window shifted by the site's UTC offset |
  | *any* | `post_modified_gmt > …` | **every never-published record, on every pull** |

- **The third is the serious one.** WordPress writes `0000-00-00 00:00:00` into the GMT columns of a post that never had a publish time, and `>` is false against that sentinel for every possible bound. So those records were not served late — they were never served, on any incremental pull, forever. On this install that is **45 drafts of 1,453 rows**. This is the repo's defining failure mode exactly: a `200`, a well-formed page, and content silently missing.
- **It was found by the consumer, not by this repo.** `wordpress-importer`'s `ImportWordPress.php` carries it in the CLI help for `--modified-after` as a WARNING to its own operators. A workaround documented on the far side of an API is a defect on this side.
- **Why the fix is a second `date_query` clause and not `posts_where`** — `suppress_filters => true` is on for this query (D-045) and discards `posts_where`. `WP_Date_Query` cannot express `= '0000-00-00 00:00:00'` either, so the sentinel is selected by an epoch bound: `<= '1970-01-02 00:00:00'` matches it and nothing else, because no genuine WordPress post predates 1970.
- **The trade, stated** — those records are re-sent on every incremental pull. That is cheap and in the safe direction; the alternative is the failure above.
- **Why the ISO shift happened at all, since the column was chosen to prevent it** — `post_modified_gmt` was picked precisely so an ISO timestamp would not be shifted by the site's offset. The shift is introduced *downstream* of the column: `WP_Date_Query` resolves the instant, then re-renders it in **site-local** time before comparing it against the GMT column. Choosing the right column cannot fix a conversion that happens after the column is chosen.
- **A bare timestamp is read as GMT**, matching what the parameter is documented to mean. Assuming the site's zone for it would reintroduce the second bug.
- **The first version of this fix introduced a fourth defect, in the direction this entry says is impossible — found by the pre-merge review, 2026-08-21.** It normalized the caller's timestamp to a GMT `Y-m-d H:i:s` **string** and handed that to `WP_Date_Query`, which runs a string through `build_mysql_datetime()` — `date_create( $s, wp_timezone() )->setTimezone( wp_timezone() )->format(…)`. That round trip is the identity everywhere *except* inside a daylight-saving spring-forward gap, where the wall clock does not exist and PHP rolls it forward an hour. This install's `timezone_string` is `America/Chicago`, so `modified_after=2026-03-08T02:30:00Z` compiled to `> '2026-03-08 03:30:00'` — **an hour too NARROW**, dropping records.

  Note the shape of it. *Before* this entry's work the bound was too wide (over-serving, harmless); the fix made it too narrow for one hour a year. The heading of this entry and the docblock both claimed the window "can only ever be too wide", and for that hour both were false.

  Fixed by passing **part arrays** rather than strings: `build_mysql_datetime()`'s array branch is a plain `sprintf()` and touches no timezone. `NEVER_PUBLISHED_BEFORE` is a part array for the same reason — it happens to round-trip safely, but only by luck of the zone.

  **The existing regression test could not have caught it**, and that is the durable lesson: it set `gmt_offset = -5` with an empty `timezone_string`, i.e. a FIXED offset, which has no DST gap to fall into. Only a named zone exposes this, so the new test sets `America/Chicago` explicitly.
- **`gmtBound()` was also far too permissive, and every failure was silent.** It handed the raw string to `DateTimeImmutable`, which accepts everything `strtotime()` does — so `now`, `tomorrow`, `+1 week`, `Thursday` (next Thursday), `@1700000000` and `12:00:00` (today at noon) all became bounds, and the endpoint answered `200` with a self-consistent `X-WP-Total` and almost no records. Worst of them: **`2026`**, a valid ISO 8601 reduced-precision year and a format the parameter description advertises, which PHP reads as the clock time **20:26 today**. The accepted shapes are now enumerated by regex and the date checked with `checkdate()`; anything else is a `400`.
- **`include` had the same class of bug and the first fix did not close it either.** Testing the VALUE against `[]` looked right, but WordPress sanitizes `include` against its registered `array` schema *before* the controller runs, so `?include=`, `?include=,` and `?include=%20` all arrive as an empty array — by value, indistinguishable from never having been sent, and the whole post type was still served. Only `has_param()` answers the question actually being asked. Verified against `rest_sanitize_value_from_schema()`.
- **A post type must be exposed WITH its taxonomies, and the first attempt at `logo-list-item` was not.** `PostPayload::terms()` intersects a record's taxonomies with the configured list, so exposing the type alone served all three records with an empty `terms` object and their `logo-list-category` assignment silently gone — the failure mode this project exists to prevent, created while fixing another instance of it one commit earlier. `logo-list-category` and `logo-list-label` are now configured alongside the type, and a guard test fails on any exposed type whose taxonomies are neither exposed nor listed as deliberately excluded.

  **A live-install sweep then found the same shape pre-existing and wider**: `location → region` (6 assignments), `location → location_type` (2), `location → gmb_cat_location` (5), `provider → gmb_cat_provider` (9), plus `page`/`post → following_users` (33) and `wp_global_styles → wp_theme` (1). Whether the Find-a-Doc ones are content the migration must carry is a real question and is **not** settled here — it is #73. The guard cannot see them either: `location` and `provider` are not registered in the Feature suite's process, which is #12 territory.
- **`logo-list-item` was missing from the exposed post types entirely**, found by the importer against a real `--source=api` run: 3 records on site 1, a registered type, with a dedicated entry creator waiting for it, omitted silently. `config/defaults.php` now lists it, and also names the types deliberately excluded (`revision`, `acf-field`, `acf-field-group`, `oembed_cache`, `wp_navigation`) so the next person does not re-file this. ### D-055 — Ninja Forms gets an endpoint after all, and it exists to serve the one thing a `.nff` cannot

- **Decided** — `GET /forms/ninja` and `GET /forms/ninja/<id>`. This **reverses D-050's "Ninja Forms is not built"**, on the trigger D-050 itself wrote down.
- **The trigger fired, exactly as recorded.** D-050 said "if the importer adopts this API for posts and pages, forms follow in the same change". It has: `--source=api` reads posts, terms, authors, options, post-types, taxonomies and sites. The importer then chose to source form definitions from the API too, but only once all three plugins are served — a partial adoption would leave a second sourcing path maintained forever for a handful of files. Ninja was the sole blocker (`wordpress-importer#695`).
- **The endpoint's whole reason is the id.** Every `.nff` in the captured corpus is JSON — despite the extension — of exactly `{settings, fields, actions}`, with **no id at any level** and an empty `settings.key`. Post content refers to forms *by number*: `[ninja_form id=3]`, `<!-- wp:ninja-forms/form {"formID":3} -->`. So the importer scrapes ids out of content, asks an operator for a file per id, and can only warn about a mismatch it has no way to detect. Serving `id` alongside the definition deletes that mechanism entirely (`wordpress-importer#10`). The rest of the shape matches a `.nff` so no second mapper is needed.
- **Free, so it is a dev dependency and has no skipping tier.** `wpackagist-plugin/ninja-forms ~3.15.0`, loaded from `vendor/` like ACF free. Gravity Forms and Formidable are paid, so their tests skip where the plugin is absent; this is the one form endpoint whose coverage on a CI runner equals a developer's. The surrounding install still wins if it has Ninja Forms activated.
- **Read off the tables with a fresh model per id, NOT through `Ninja_Forms()->form()`.** Three separate traps, all found by reading the plugin:
  1. `NF_Abstracts_ModelFactory::field()` **mutates the factory**, swapping `_object` from the form to a field — and `Ninja_Forms::form()` memoizes factories in a `static`, so one call leaves that factory pointing at a field for the rest of the process.
  2. `NF_Abstracts_Model::find()` hydrates settings only when caching is OFF, and `WPN_Helper::use_cache()` is `return true;` on its first line with the real logic dead below it. The bulk path therefore never runs `get_object_settings()`.
  3. `get_fields()` and `get_actions()` default `$fresh` to `false`, serving whatever the model already holds.
- **The first version of this shipped the repo's signature failure, and the tests caught it.** `NF_Database_Models_Form` has **no** `get_fields()` or `get_actions()` — those are factory methods — and the payload called them on the form model behind a `method_exists()` guard. Every form served `fields: []` and `actions: []`: a well-formed `200` with the definition's contents missing. The guard is gone; a missing class is a fatal now. Reverting to that shape reds `it serves a form's fields and actions`.
- **A missing id is a `404`, and that needed care.** `new NF_Database_Models_Form( $wpdb, 999999 )` constructs happily for an id nobody has and answers with empty settings, so a route trusting the model would serve `200` for a form that does not exist. Both routes test membership against `ninjaIds()` first — one source, so index and show agree by construction.
- **Volume** — 161 Gravity forms, 12 Formidable, 4 Ninja across the corpus. The smallest of the three, and the only one whose export format cannot identify itself.
- **Two pre-merge review rounds found six more defects in this endpoint, and three of them were in the FIXES for the first round.** Recorded because the pattern is the point:
  - **Fields and actions were served a level too deep** as `{id, settings}`. A real `.nff` carries them FLAT with settings inline, and the plugin's own `export()` does `$export['fields'][] = $field->get_settings()` with no wrapper. The importer's reader does `$field['type']`, `$field['key']`, `$field['options']` — every one would have been `null`. A 200 with every field present and every field unreadable, i.e. this endpoint's stated justification failing against its own bytes.
  - **Fields were ordered by row id**, not by the `order` a `.nff` carries, so a form reordered after creation arrived scrambled.
  - **Then the ordering fix read the WRONG COLUMN PAIR.** `nf3_field_meta` carries `key`/`value` *and* the denormalized `meta_key`/`meta_value` copies added in 3.3.12. Ninja Forms reads settings from the first pair — `get_settings()` selects `Meta.key, Meta.value`, and the generic branch has the copies commented out deliberately — so the `order` this endpoint SERVES comes from `value` while the sort read `meta_value`. On a row where the copy is NULL, a state the plugin's own `get_existing_meta()` guards for, `COALESCE` sent every field to the default and the sort collapsed back to id order. **The first ordering test could not tell the two apart**, because `_save_setting()` writes all four columns in sync; the regression test now nulls the copies to force them apart.
  - **The test helper created one form per PHP process.** `Ninja_Forms::form()` memoizes factories in a `static`, so `form('')` returned the same model every call and the second `save()` UPDATEd the first row — the paging and collection tests were asserting over a single record while appearing to use several.
  - **The stub declared the API wrongly in three places**: `get_fields()`/`get_actions()` on the form model (they are factory methods, and this is the exact call that shipped the empty-payload bug), `save()` returning `$this` when it returns `array|null`, and an optional `$id` on `Field`/`Action` constructors where the real ones require it. A stub with a wrong signature is worse than no stub — it makes the analyzer agree with code that raises a fatal error.
  - **The namespace index advertised `gravity` and `formidable` while serving `ninja`**, so a consumer trusting discovery would never have asked for it.
- **Ref** — #76, D-050, D-046, D-044, D-006, D-004, `wordpress-importer#695`, `#10`

### D-056 — Gravity Forms add-on feeds are served on sibling routes, with their meta filtered and disabled feeds kept

- **Decided** — `GET /forms/gravity/feeds` and `GET /forms/gravity/<id>/feeds`. Every feed on the site or on one form, active and inactive alike, with `meta` filtered for credentials and the withheld count reported.
- **Why it exists at all** — a feed is the only part of a form's behavior that never travels in an export. `GFAPI::get_form()` reads `gf_form` and `gf_form_meta`; feeds live in `gf_addon_feed`, and a Gravity Forms export of the largest affected site contains **zero** occurrences of `userregistration`, `feeds`, or `gravityformsuserregistration`. Three sites in the captured corpus create real WordPress accounts on submission, so a migration without this leaves three forms that collect a username and a password and create nothing. It is not deferred data; it is data that is lost (`wordpress-importer#821`, `uams-statamic#205`).
- **Sibling routes rather than a `feeds` key on the form record, and that is load-bearing.** `GET /forms/gravity/<id>` serves `GFAPI::get_form()` output verbatim, which is byte-for-byte the native form array an export file contains. `wordpress-importer#809` is built on exactly that equivalence — its 12.6k-line field-type mapper sees identical input from either source — and `GravityFormsFixtureParityTest` is what holds it. Adding a key inside the form array would end that property to save a consumer one request. #80 permitted either shape; this is the half that costs nothing downstream.
- **`GFAPI::get_feeds()` has D-043's defect one method along.** It is declared `( $feed_ids = null, $form_ids = null, $addon_slug = null, $is_active = true )`, so the call everyone writes **silently drops every disabled feed**. Same shape as `get_forms( $active = true )`, same direction, and here the stakes are higher: `wordpress-importer#821` has to tell a disabled registration feed from an absent one, because the difference is whether an import quietly switches account creation back on. Widened to `null`, which the plugin documents as "both", and the flag travels on the record instead.
- **Two different `WP_Error`s both mean "no feeds", and both are the ordinary case.** `get_feeds()` ends `if ( empty( $results ) ) { return new WP_Error( 'not_found', … ) }`, and it returns a *different* error when `gf_addon_feed` does not exist. That table is created by `GFFeedAddOn::setup()` rather than by Gravity Forms, so it is absent on any site that has never had a feed add-on — measured on the development network, which runs Gravity Forms and three add-ons: 25 `gf_*` tables and no `gf_addon_feed`. Both collapse to an empty list, deliberately: from a consumer's side "this form has no feeds", "nothing here has feeds" and "no add-on ever created the table" are one state, and inventing a fault out of a site that does not use the feature would be worse than useless.
- **`is_active` is served as a real boolean, and this is the one place the payload leaves a stored value behind on purpose.** The column is a `tinyint(1)` that arrives from `$wpdb` as the string `'0'` or `'1'`. `"0"` is falsy in PHP and **truthy in JavaScript**, so served raw a disabled feed reads as enabled to any consumer that is not the importer — and the thing being enabled creates user accounts. D-004 governs how a content value is shaped, not whether a storage artifact may invert a flag on the way out.
- **The meta is filtered, and Gravity Forms is the one saying it must be.** Since 2.7.16 a feed settings field can be marked `encrypt`, and `GFAPI::get_feeds()` runs every value it returns through `decrypt_feed_meta()`. **The read path this endpoint uses hands back the plaintext of fields the plugin encrypts at rest.** The encryption is inert unless `GF_ENCRYPTION_KEY` is defined, so on most installs nothing was ever ciphered — but the *marking* is the point: an add-on author writing `'encrypt' => true` is naming that field a credential, and this endpoint would otherwise serve it.
- **The add-on's own list is deliberately not consulted.** `GFAddon::get_addon_by_slug()` plus `get_fields_to_encrypt()` would be more accurate than any list this repo keeps. It is not used because `get_fields_to_encrypt()` derives from `get_feed_settings_fields()`, the add-on's settings **UI** definition, and several add-ons populate that by calling their remote service to list accounts, audiences or products. A migration read must not make a request to a payment gateway as a side effect of serving a page. So the plugin's marking is the evidence that a filter is needed rather than the mechanism, and the filter is D-032's, reused rather than transcribed: `OptionsPayload::secretIn()` and `isDeniedNestedKey()` were made public for a second caller on the same reasoning `classify()` was for the audit script.
- **A plain name denylist breaks the ticket, and the fix is a MEMBERSHIP test rather than a value heuristic.** User Registration stores `password` as the id of the form field the password comes from — the string `'4'`. `option_denylist_nested_keys` carries `%password`, so applied naively the endpoint withholds the single mapping the consumer most needs while withholding nothing sensitive at all. That is D-032's own false-positive class for the third time, after `%user_roles` and `seopress_manage_license`, and it fails `wordpress-importer#821` outright. **The exemption is that the field EXISTS on this feed's form**, not that the value looks like a field id: `4` is exempt because field 4 is there, `4.3` because that input is, and anything else is judged on its name and shape however numeric it looks.
- **The first version counted digits, and the claim it rested on was false.** It exempted `^\d{1,5}(?:\.\d{1,3})?$` under a docblock reading *the string `'4'` cannot be a credential whatever it is called* — but a five-digit PIN or a short account number under `%password` is exactly that string and exactly a credential, so the bound was a guess about where field ids stop rather than a fact about the data. The form is already loaded on both routes, which is what makes the honest test available: `allFeeds()` resolves each distinct form for the trash filter and hands its field ids back, so the payload never loads it twice.
- **The rules run at every DEPTH, and the first version ran three of them at one.** `deniedByName()` wrapped the shared walk instead of living inside it, so one rule had two behaviors — at depth 0 an `int` was coerced and a bare `4` waived, at depth 1 neither. Three disclosure paths lived in that gap, all measured against the running code: a nested numeric credential under a credential-named key, an array under a key ON the denylist whose children's keys were benign, and a JSON container nested one level down that no leaf rule can match because the leaf IS the container. `OptionsPayload::secretIn()` now takes the exempt values and a decode flag and applies both at every depth; the option path passes neither and is unchanged.
- **An array under a matching key is judged by that key, which restores parity with `classify()`.** An option named `credentials` is withheld by name whatever its value is; this filter returned early on any non-string and so tested only the children's own keys. The cost is a settings group named like a credential holding nothing but mappings, withheld whole — the safe direction, and visible in `denied.by_name`, which this decision already names as the signal that a mapping was withheld.
- **Withholding is per meta ENTRY, not per feed**, which is the one place this diverges from `OptionsPayload`. An option row is atomic — the row is what somebody configured, so a credential anywhere inside it withholds the whole thing. A feed is a record of many independent settings, and discarding the field mapping over one gateway key would throw away the reason the endpoint exists. Counts are still reported split by reason and never by name, for D-032's reason: naming them would hand a reader the map of which credentials this site holds.
- **Three `GFAPI` feed methods were unguarded, and one of them creates users.** `entryApiMarkers()` catches `get_entry_feed_status` because of where the word `entry` sits in the name, and missed `maybe_process_feeds`, `get_processed_feeds_meta` and `update_processed_feeds_meta` because of where it does not. `maybe_process_feeds( $entry, $form )` runs a form's feeds against an entry: for this add-on that means **creating a WordPress user**, and for a payment add-on it means charging a card. It reads like a query and it is an action. The feed writes were unguarded too, in a plugin where nothing else can write at all. `feedReadMethods()` and `feedWriteMethods()` now classify the whole surface, and a new feed method fails the suite until somebody decides which it is.
- **And the guard that was supposed to stop that list falling behind had never run once.** `FormEntryBoundaryTest` re-derives the entry methods by reflection and lives in `tests/Unit`, where WordPress is deliberately never loaded — so `class_exists( 'GFAPI' )` is false on every machine on every run, and the skip was unconditional rather than environmental. The file's docblock promised the list "cannot silently fall behind again" on the strength of a test that had never executed. The lists moved to `tests/Support/form-api-surface.php` and the reflection guards to `tests/Feature/Forms/FormApiSurfaceTest.php`, where they now skip only on CI, which is the arrangement D-030 and D-044 describe and pay for. Both pass on a real `GFAPI`, so the entry list is confirmed accurate for the first time.
- **The test bootstrap installs `gf_addon_feed` itself**, for the reason it already runs `FrmMigrate` and `NF_Database_Migrations` (D-046): the table is created on add-on setup, and the bootstrap never activates anything. Through an anonymous `GFFeedAddOn` subclass rather than a copy of the plugin's `CREATE TABLE`, and with no property overrides — `GFAddOn::setup()` calls `install_translations()`, which downloads a language pack when `$_enable_rg_autoupgrade` is true, and leaving every property at its default is what keeps the bootstrap from making an outbound request. Without this step the feed tests would not fail; they would **pass**, because a missing table returns the same empty list a form with no feeds legitimately has.
- **Residual** — no real feed has been read. The three affected sites are in the importer's captured corpus, not on the development network, which has never had a feed add-on active. Every assertion here runs against fixtures this repo creates, so the payload shape is proven and the *content* of a production User Registration feed is not. The filter's false-positive direction is the one to watch when it first meets one: a mapping withheld shows up as a non-zero `denied.by_name`, which is visible without naming anything.
- **Second residual, and it is the one with no signal.** On an install where `GF_ENCRYPTION_KEY` *is* defined, `decrypt()` ends in `json_decode( GFCommon::openssl_decrypt( … ) )`, which returns **`null`** when the key is wrong rather than raising. A site restored without its original key would therefore serve `username: null` in place of `'3'` — a well-formed feed with its mapping silently blanked, which is this project's defining failure mode in the one place nothing here can detect it. Untestable from this repo: the development network defines no key, so the branch cannot be reached, and building detection against an unreachable branch would be guessing at its shape. Named here so that a payload of nulls is read as a key problem rather than as an empty configuration. A `meta` column that is null, or that fails to decode, arrives as an empty array for the same reason and with the same ambiguity.

### D-059 — The mutation criterion is no unexplained survivors, and a dependency claim carries a revision

- **Decided** — two standing conventions, set by the operator on 2026-09-05 and recorded together because they arrived together, not because they are related.
- **The mutation criterion** — every surviving mutant ends in one of three states: killed by a new test, deleted as dead code, or annotated on its line with `// @pest-mutate-ignore` and the reason it cannot be killed. A survivor is a test to write, or dead code to delete. The wording matches `wordpress-importer`'s existing rule rather than restating the same idea a second way.
- **Why not a score** — a percentage aggregates the two classes it most needs to separate. An unexamined survivor and a provably equivalent one are the same number under a threshold while being opposite states. Raising the bar makes it worse rather than better, because the last few percent are usually the equivalent mutants, so a high threshold converts "explain this survivor" into "delete a defensive guard to move the number". This repository already has the extreme case on record: D-023 accepts that `Site` and `Plugin` report a permanent nought percent for a structural reason, so a score that cannot be met and should not be chased is not hypothetical here.
- **Rejected** — a `min()` gate, and mutation in `composer ci`. Decided against, and this does not reopen it; D-023 previously recorded both as undecided, and they are now decided in the negative.
- **The instrument** — `// @pest-mutate-ignore` is a per-line source comment, with `:MutatorName` scoping it to named mutators. The config-level `ignore(...$paths)` and `except(...$mutators)` are not substitutes: each silences a whole path or a mutator repository-wide, so neither can carry a per-survivor justification and neither is visible at the line a reader is looking at.
- **The dependency-revision convention** — a claim about a dependency's code carries the revision it was measured at. "Present in `<package>`" is incomplete the way an absence without a search scope is incomplete: a pinned or vendored copy can report the correct version, and the correct source reference, while containing different code. Name the commit, tag or lock entry, and say which tree was read — the installed copy, or the upstream default branch.
- **Consequences** — `adversarial-review` gains both, `pest-testing` gains the annotation mechanics, and `filing-defects-across-repos` step 7 is reconciled so that naming a version does not read as sufficient for a dependency claim. D-023's scoping decision is untouched.
- **Also corrected here, because the criterion could not be written without it** — `adversarial-review`'s tooling section described mutation testing as not wired here and "gated on #15 and deferred by #18". Both are closed, and #18 concerns the CI chain rather than mutation testing. `composer mutate` is wired, PCOV is present on the development machine, and D-023 records a completed run. Writing a criterion into a bullet that says the tool is unavailable would ship a self-contradicting rule. The property-based half of that section is accurate and is left saying so.
- **Ref** — #122, #121

A slot elsewhere needs `LOCAL_CI_WP_ABSPATH` before a hand-run suite starts; a slot inside needs nothing. The runner is unaffected either way: it resolves the WordPress root from the repository rather than the worktree and passes `WP_TESTS_ABSPATH`, which is what makes `--worktree-path` safe.
- **Why the primary is NOT a pure reference tree, unlike both sibling repositories** — `scripts/verify-site-scoping.php` (#12, D-049) and `scripts/verify-taxonomy-coverage.php` (#73) need the plugin **loaded by WordPress**. No slot arrangement runs them: not a slot outside `wp-content/plugins/`, and not a dotted slot inside it either. The primary is the only tree WordPress loads. Both siblings' primaries are applications rather than plugins inside one, so the constraint does not exist for them and their rule ports no further than its first sentence.
- **Rejected** — the primary as slot A. Simpler to state, and it destroys the oldest drift signal available: "the primary is on a branch I did not set" stops meaning anything once concurrent sessions routinely put it there. Both sibling repositories forbid exactly this and their reason applies here unchanged.
- **Rejected** — dotted slots only, deferring the two live-install scripts. A clean port with no exception, at the cost of two checks that stop running until someone re-solves them. A check that does not run is indistinguishable from a check that passed, which is the defect class this repository filed three issues about on the day this was decided.
- **Occupancy** — a slot at rest is detached at `origin/main`. Git permits a branch in exactly one worktree, so a slot holding a branch is a slot in use and `git worktree list` answers occupancy with no lock file.
- **Not decided** — how the primary is claimed and released for a loaded run. It holds `main` by definition, so a branch cannot be its occupancy marker the way it is for a slot. Left open deliberately rather than answered ahead of the need.
- **Consequences** — #98's cwd-attribution gap is narrowed but not closed: slots remove the common case, and the primary is still shared by construction. #119's single-flight refusal is still required — slots are prevention, that guard is a refusal, and neither substitutes for the other.
- **Ref** — #126, #119, #98, #12, #73

### D-061 — Windows tool resolution is ported from `wordpress-importer`'s `spawn-helpers.mjs`, not patched locally

- **Decided** — `scripts/spawn-helpers.mjs` and `scripts/spawn-helpers.test.mjs` are brought into this repo verbatim from `wordpress-importer`. `local-ci.mjs`'s private `which()` is replaced by the imported one, and `run()`/`capture()` route through a shell, quoting via `winQuote()`, whenever `needsShell()` says the resolved executable is a `.cmd`/`.bat` shim.
- **Why a port rather than one of the three fixes #143 originally proposed** — every one of `shell: true` for known wrappers, splitting `LOCAL_CI_COMPOSER` into an argv array, and documenting a raw-exe requirement patches **invocation** alone. The failure measured on a Windows development machine is in **resolution**: the private `which()` shelled out to `/usr/bin/env sh -c 'command -v …'`, a Git-Bash/MSYS2 path native Windows Node cannot resolve at all, so `git` and `php` failed before Composer was ever reached — confirmed directly (`which('git')`, `which('php')`, `which('composer')` each threw `ENOENT` under the old code, measured on this machine, not inferred). Composer was only the first tool to surface it.
- **Why the port over a fresh implementation** — two properties neither of the three original candidates could offer. It is **exercised on Windows, not merely written**: `wordpress-importer`'s copy reaches `composer install`, autoload generation, and a nested `@php` sub-invocation on a real Herd checkout, confirmed on the same Windows machine for this repo's own port too — `composer install` completed the full dependency tree during verification. And the **two source copies have not drifted** — `wordpress-importer` and `uams-statamic`'s implementations differ by 29 lines, all docblock; stripped of comments both are 33 identical lines (`uams-statamic-archive#1948` is the ticket that made it a shared module for exactly this reason). One non-obvious detail a reimplementation would likely miss: `which()` returns the resolved extension in the case `PATHEXT` supplies — `composer.BAT`, not `composer.bat` — and `needsShell()` matches it case-insensitively on purpose.
- **Rejected** — `shell: true` for known wrapper candidates, an argv-array override, and a documented raw-exe requirement. Each would have left `which()` unable to resolve `git` or `php` on the same platform, and none had been exercised anywhere before this decision.
- **Residual left open by the port, closed below** — `resolveTool()`'s `candidates` path (used for `LOCAL_CI_COMPOSER` et al.) checked `existsSync()` alone, with no extension filter, so an override pointed at `composer.phar` still passed resolution, `needsShell()` correctly returned `false` for it (`.phar` is not a shell extension), and `spawnSync` failed with `EFTYPE`. Measured directly on that Windows machine: no `.PHAR` file association exists (`assoc .phar` reports none), and `cmd.exe` silently returns exit `0` with no output for an unassociated file under `shell: true` — a false-positive trap, not a working third option.
- **The `.phar` residual — decided: refuse a non-executable candidate at resolution.** `resolveTool()`'s `candidates` loop now requires that an entry be directly executable *on the running platform's own terms*, via the new `isExecutableCandidate()`, and falls through exactly as it already did for a missing candidate when one is not. The test is "can this OS execute this path", never "does this path end in `.phar`" — the two platforms disagree about what an extension means. **POSIX** — executability is a mode bit; the extension is decoration. Verified: a `.phar` carrying a shebang at mode `755` passes, the identical bytes at `644` do not — and this machine's own working `composer` is itself a phar with a shebang and the execute bit set, named `composer` with no extension at all, so a suffix check would have regressed it. **Windows** — there are no mode bits, so the extension is the whole signal, read against the same `PATHEXT` list `which()` already resolves against; a bare `.phar` fails it exactly as intended, and the existing `.bat`/`.exe` candidates are unaffected (`scripts/local-ci.test.mjs` covers both platforms' branches directly).
- **Rejected (the `.phar` residual)** — spawning through the resolved PHP interpreter (rejected: `resolveTool()` would stop returning a single path, and the only reason the override was ever pointed at a phar was `which()` being broken, which the port already fixes; remains available if a real need appears). Adding `.phar` to `needsShell()` (rejected: unreachable through `which()` since `PATHEXT` carries no `.PHAR`, depends on a per-machine file association, and `shell: true` alters quoting for every tool on POSIX). Documenting the limitation and changing nothing (rejected: spends `resolveTool()`'s own stated promise to fail at resolution rather than deep inside a job).
- **Ref** — #143, #131, `uams-statamic-archive#1948`

### D-063 — The plugin issues its own per-network token, and writes the one option it has

- **Decided** — #140 chose a plugin-issued credential over the `wp-config.php` shared constant and over an application password; this records what building it settled. The token is generated from an admin page, displayed once, stored as a SHA-256 hash, and regenerated with an overlap window. It is presented in the existing `X-UAMSWP-Migration-Key` header, so no consumer changes.
- **This is the exception to "no options written"** — `CLAUDE.md` and `Plugin.php` both described a plugin that writes no options, and a credential has to live somewhere. The exception is exactly one option, written only when an operator issues a token, never on load and never by a request the API serves. `Plugin.php`'s docblock is amended to say so; **`CLAUDE.md`'s line is left as it stands, because amending a standing rule is not a builder's call.** The contradiction is real and is deliberately visible rather than resolved silently.
- **Hashed on both branches, and the branch that needs it is the one a multisite check would disable it for** — `update_network_option()` falls through to `update_option()` when `! is_multisite()`, so on a single-site install the record lands in `wp_options`, the table `GET /options` serves. Gating the hash on `is_multisite()` would therefore remove it from precisely the install where the endpoint could disclose it. `news.uams.edu` is a confirmed single-site install in this estate, so this is not hypothetical.
- **Three independent controls keep it out of the payload, and they are tested separately** — only a hash is ever stored, so there is no plaintext to serve; the option name ends in `token`, which `option_denylist`'s `%token` matches; and a 64-character hash is withheld by the shape heuristic whatever it is called. Splitting the tests matters: a test written with a realistic value passes on the shape rule alone and cannot tell whether the name is denied at all. The first version of that test did exactly that, and the positive control is what caught it.
- **Rotation accepts two tokens for a window** — regenerating stores the outgoing hash with an expiry and the comparison loops rather than returning on the first `hash_equals`. Without it, every request between regeneration and the operator pasting the new value is refused, which is the defect #140 rejected the shared constant for, reproduced at n=1 and surfacing mid-capture rather than at setup. Default one hour, filterable. A window of zero is a coherent choice and drops the outgoing token rather than storing an already-expired entry.
- **A malformed record fails closed** — a `previous` entry whose expiry is missing or not an integer is treated as expired, never as unlimited. The failure direction for a damaged credential record has to be refusing access.
- **Not a password KDF, deliberately** — the token is 256 bits of `random_bytes`, so there is no low-entropy secret for a slow hash to protect, and this credential authenticates a bulk read across every endpoint and every site. Per-request bcrypt would be a real cost for no gain.
- **The plaintext is never stored, not even briefly** — the admin form posts to its own page and renders the token inline. The usual redirect-and-transient pattern would put the credential in the options table, which on the single-site branch is the table the API serves.
- **The guard was extended rather than routed around** — `NetworkOptionGuardTest` watched `update_site_option` but not `update_network_option`, which core implements the first in terms of. Building to the ticket's instruction would have written a network option with the guard reporting nothing, while `get_network_option` stayed watched so reading tripped it and writing did not. The watch list now covers the delegates, and it resolves a class constant instead of reporting `self::OPTION` as a dynamic name — without which the allowlist entry would be unreachable text.
- **Residue, named rather than ticked** — the Feature suite runs as multisite and `is_multisite()` reads a process constant, so the single-site branch is not executed by any test. What is asserted is that the write path has no `is_multisite()` branch in it, that the stored record contains no plaintext, and that the endpoint withholds the option when it is placed where that branch would put it. Inspecting storage on a genuinely single-site install is deferred. The hash also survives deleting the plugin directory, since there is no uninstall hook — accepted, as a stored hash authenticates nothing on its own.
- **The capability filter now reaches further than it did, and this is the one open question the build did not settle** — `uamswp_migration_api_capability` filtered who may READ the API; the admin page makes it filter who may MINT a credential, and a token outlives the account that issued it. The page uses `Auth::capability()` because #141 asks for a single expression so page and API cannot drift. The alternative is pinning the page to the unfiltered baseline, which is safer in the lowering direction and means a deployment that RAISES the bar can mint tokens it cannot use. Left as the ticket specifies, because the filter is reachable only by code already installed on the site — a higher privilege than any token grants — so this is a misconfiguration rather than an attack surface. Worth an operator's word if the filter is ever used.
- **Ref** — #141, #140, `UAMS-Web/wordpress-importer#702`, `UAMS-Web/wordpress-importer#982`

### D-066 — Line endings are the repository's policy, not the checking-out machine's

- **Decided** — add `.gitattributes` with `* text=auto eol=lf`, so every checkout normalizes to LF regardless of the checking-out machine's `core.autocrlf`. Tracked in #152.
- **The defect this closes is not "files have the wrong line endings"** — the committed blobs were always LF. It is that without a policy file the decision belongs to whoever clones, and Git for Windows defaults `core.autocrlf` to `true`, so a contributor who has never touched that setting gets a corrupted checkout by default. The exposure is the common case rather than an edge one.
- **What makes it expensive is that the corruption never names itself.** Measured on a Windows development machine while validating #144 and #149: `pint --test` reported six fixers against code with no style violations, and `tests/Unit/CiParityTest.php` failed six of seven assertions because its exact-string line matching met a trailing `\r`. - **Reproduced on macOS before the fix and after it, with the setting held constant.** `core.autocrlf` is a git setting rather than an OS-gated one, so a local clone with `core.autocrlf=true` exhibits it: `includes/Auth.php` 190 CR bytes, `scripts/local-ci.mjs` 1094, `CLAUDE.md` 171 — and 0, 0, 0 from the identical clone once `.gitattributes` is present. That is the mechanism demonstrated rather than argued, and it is why the fix did not have to wait for a session on Windows.
- **The blanket rule is the guard; the explicit list is documentation.** `* text=auto eol=lf` is what makes a *new* file type covered on the day it arrives. - **Out of scope** — #147's path-separator instances. A separator is a different defect class from a line ending, and conflating them is how a fix for one gets credited with the other.

### D-068 — A red hand-back is marked with a label, never a draft flip

- **Decided** — operator instruction on 2026-09-09, taken for all three `UAMS-Web` gate repositories at once. The gate annotates a red verdict; it does not mutate the pull request. This closes the fork D-065 recorded as explicitly open — "whether a red verdict flips the pull request to draft ... that fork is the operator's" — and supersedes the *reasoning* D-062 and D-064 carried, not the behavior they described.
- **What changed here is the argument and the scope, not the rule.** `.claude/skills/local-ci/SKILL.md` already said not to flip, on the grounds that flipping is "a larger touch than reporting a failure warrants". So the flip spends the GraphQL quota `.claude/rules/github-api-budget.md` exists to protect, on a signal that is already wrong on the ground above.
- **The case that made the flag look necessary predates its replacement.** The verdict records `UAMS-Web/wordpress-importer#993` sitting 2h 52m after a hand-back and cited as evidence *for* flipping, against `#1032` — same gate, same author — acknowledged in 3m 11s without it. ### D-082 — `composer.json`'s `mutate` script is prefixed `@php`, because that is what actually reaches the per-mutant child on Windows; a second, narrower false-kill remains and is not fixed by it

- **Decided** — on 2026-09-15, `composer.json`'s `mutate` script is written as `@php vendor/bin/pest …` for each of the three files it covers, replacing a bare `pest …` script. `#179` fixed a real, separate problem (this repository's own documented invocation examples). `#287` then found that `#179`'s recommended replacements (`composer mutate`, `composer exec -- pest …`) were not sufficient on their own, traced why, corrected an intermediate misattribution of the mechanism, found the actual fix, and separately confirmed a second, still-unexplained failure that the fix does not touch.
- **The mechanism, corrected once already in the course of this investigation** — the mutate plugin spawns one child per mutant, and `MutationTest::start()` builds that child's command from `$originalArguments`, prepended to `--bail` and the per-mutant `--filter`. `$originalArguments` traces back to **the outer `--mutate` process's own `argv[0]`**, not to any string the plugin hardcodes. `Support/Configuration/CliConfiguration.php:64` (`pestphp/pest-plugin-mutate` v3.0.5) builds a `$filteredArguments` array starting with the literal `'vendor/bin/pest'` that looks like the source of the child's command at a glance — it is not: that array is consumed locally to construct a Symfony `ArgvInput` for parsing option flags and is discarded; `fromArguments()`'s own `return $arguments;` returns the *original*, filtered argument list, never the literal. This intermediate misattribution was published — in this repository's own docs and in an upstream report — before being caught and corrected here; see the upstream-report note below.
- **The actual failure** — a forward-slash `argv[0]`, which any bare `vendor/bin/pest` call on Windows produces, fails to launch as the first element of a per-mutant Symfony `Process` array command (`'vendor' is not recognized as an internal or external command`); the identical backslash-separated string launches correctly. Composer's `@php` script-directive handler normalizes the separator before PHP ever runs, which is what a bare `pest …` script (no `@php`, no explicit `vendor/bin/` prefix) does not get. Confirmed directly, twice: an isolated `Process(['vendor/bin/pest', …])` call outside Pest entirely reproduces the failure and its backslash counterpart does not; and editing `composer.json`'s script to add the `@php` prefix changed a 38-mutant `Auth.php` run from 38-of-38 failed launches (all silently scored killed, `100.00%`) to a genuine run with real per-mutant timing.
- **Why a failed launch reads as a kill rather than an error** — `MutationTest::hasFinished()` maps `$process->isSuccessful()` (any zero exit) to `Untested` and anything else to `Tested`. A launch failure is a non-zero exit, indistinguishable from a genuine kill by this logic, and each failure costs on the order of a couple of seconds under `cmd.exe` — enough wall-clock time across dozens of mutants to look like a real run rather than an instant crash. This is why `composer mutate` (bare, pre-fix) did not read as obviously broken: it fabricated a plausible score at a plausible speed.
- **A second, narrower failure survives the fix and is not resolved by this decision.** With the launch failure eliminated — confirmed by the same isolated `Process` probe and by real per-mutant timing in an actual run — one specific mutant in `Auth.php`, covered by exactly one test, still reports *killed* after that test is deliberately skipped and the skip is confirmed to have genuinely taken effect. Reproduces under `composer mutate` itself, with the `@php` fix in place; the other 37 mutants in the same run correctly resolve. The mechanism is not yet isolated. Tracked in `#287`, which stays open for it; this decision covers only the launch-failure half.
- **No further repository-local mitigation is adopted for the second failure.** A vendor patch (`cweagans/composer-patches` or equivalent) was considered and left undecided rather than adopted — it is new build infrastructure with an ongoing maintenance cost, and a decision this repository has not made before; raise it separately if warranted once the second mechanism is understood.
- **An upstream report was filed, and its central mechanism claim is wrong** — [`pestphp/pest#1916`](https://github.com/pestphp/pest/issues/1916) (issues are disabled on `pestphp/pest-plugin-mutate` itself; `pestphp/pest#1843`, still open, is a related-but-distinct root cause reaching the same class of symptom — a non-`isSuccessful()` process outcome read as a kill). The report attributes the failure to the hardcoded `CliConfiguration.php:64` literal; that attribution does not hold, per the correction above. A follow-up comment correcting the mechanism to argv[0] inheritance, and noting the true fix (or a framework-level fix — normalizing separators before building a child command, regardless of what the outer process handed it), is owed and is tracked as residue rather than done here.
- **Standing discipline regardless of the fix above** — a `--mutate` score, or a clean survivor list, is still not sufficient proof by itself, because of the second, unresolved failure. Before relying on any single mutation result, skip the one test known to kill a specific mutant, confirm the skip genuinely took effect (a plain, non-mutate run reporting that test skipped), re-run `--mutate` scoped to that file, and confirm the mutant now reports as a survivor rather than an unchanged score. `pest-testing`'s mutation-testing section carries the worked recipe. This is not a one-time verification — a false kill leaves nothing on the survivor list to explain, so `adversarial-review`'s "no unexplained survivors" criterion cannot detect it by construction, and neither can a clean-looking run.
- **Bound** — measured on Windows, on this machine's vendored copy of `pest-plugin-mutate` v3.0.5 and `symfony/process` 7.4.13. Whether `--parallel` mode is affected by either mechanism is not yet checked. Whether either mechanism is present in a later `pest-plugin-mutate` release is unknown; re-check before assuming either still applies after a bump to that dependency. Whether the second failure reaches `Pagination.php` or `Config.php` specifically, versus being an `Auth.php`-only artifact, is not yet checked with the same positive-control method used on `Auth.php`.

A flag here would let any descendant of any suite through any other suite's lock. Keying on the pid means a child of a different holder is still refused, and a child whose holder has exited reclaims the lock rather than inheriting it.
- **Never to a parallel worker** — a process carrying `PARATEST` or `TEST_TOKEN` inherits nothing, and meets the holder as a stranger. ParaTest's main process loads the bootstrap, takes the lock, and starts its workers through Symfony Process, so every worker would otherwise inherit. Nothing gives a worker its own database, so N WordPress test installers would drop tables under each other with no message. A plain `--parallel` run is therefore refused exactly as before this decision. A `--mutate` child is inheritable only because it runs alone while its parent waits. Found by the pre-merge review of #297 and reproduced there: three concurrent workers all proceeded, where on `main` all three were refused. The Unit test starts three workers at once, with a control of the same three without the ParaTest variables.
- **Also on a lock that already names this process** — a stale lock whose pid the OS has since reused for this one is acquired without writing a file, and it exports on that path as well. Without the export, every `--mutate` child would be refused again. This came from reading the code in the same review, and a Unit test arranges the case by writing a lock that names the test's own pid.
- **Why three stores** — the export is written to `putenv()`, `$_ENV` and `$_SERVER`. Symfony Process, the route the plugin starts its children by, builds a child's environment from `$_ENV` plus the process environment intersected with `$_SERVER`. So a `putenv()`-only export is dropped, and either `$_ENV` or `$_SERVER` on its own is enough to carry it. Because the end-to-end test cannot tell if one of the two writes is deleted, each write is pinned by its own assertion. Removing either one reds that test, and removing both reds the Symfony Process test with `Refusing to run`.
- **Composer's timeout is lifted for `composer mutate`** — the script now starts with `Composer\Config::disableProcessTimeout`. Composer's default 300-second limit ended the gate's macOS run after 20 of `Pagination.php`'s 69 mutants. Checked both ways in a scratch project with `COMPOSER_PROCESS_TIMEOUT=3`: an 8-second script without the entry `exceeded the timeout of 3 seconds`, and the same script with it finished.
- **Measured** — on Windows, against `includes/Auth.php`, with each child's exit status and output captured by temporary instrumentation (since removed). Before the fix: all 80 mutants reported killed; 35 were refusals and 45 were the Windows launch failure below. After the fix: 0 refusals. The positive control that D-082 made standing discipline now passes both ways: with its only covering test skipped, line 141's `RemoveStringCast` is `UNTESTED`; restored, it is killed by that test's own assertion (`Return value must be of type string, int returned`). The run also surfaced three real survivors, filed as #295.
- **Rejected** — exempting any process that carries the plugin's `PEST_MUTATION_TESTING` variable. It names what the plugin is doing, not who holds the lock, so it would let a mutant child from one checkout past another checkout's lock on the same database.
- **Bound** — `--mutate --parallel` children carry the ParaTest variables and are refused like any worker. So a parallel mutation run is still a wall of false kills, and the `mutate` script never passes `--parallel`. On Windows two failures remain inside `pest-plugin-mutate` v3.0.5 with `symfony/process` v7.4.13: filters naming 2 to 11 tests fail to launch and read as kills, and filters above about 25 KB exceed the Windows environment block and abort the run. `Pagination.php` and `Config.php` hit the second on their first large mutant, so this fix's reach on those two files is established by the guard's structure and the Unit test, not by a per-file run. Both are tracked in #296, which carries the upstream decision.

### D-085 — `GET /posts/attachment` selects by file with `file[]`, matched on the server against each record's own size list

- **Decided** — on 2026-09-25, for #300. `file[]` takes uploads-relative paths (`2020/09/photo.png`, the form `_wp_attached_file` stores) and selects the attachments that own them. It is accepted on `/posts/attachment` only; any other type answers `400 uamswp_migration_api_file_not_attachment` rather than ignoring it and serving the whole type.
- **Why by file** — the consumer resolves an embedded image by its `src`, because a replaced image keeps its old `wp-image-N` class. Across the importer's 254-export corpus, 442 references on 17 sites name a live attachment that is not the one their `src` shows, so selecting by class id alone imports the old image silently (`UAMS-Web/wordpress-importer#1175`).
- **A generated size resolves to its attachment, and the server decides it** — a path matches a record when it is the record's `_wp_attached_file`, one of the `sizes` its `_wp_attachment_metadata` lists, or its `original_image`, each compared under the attached file's directory. Stripping `-WxH` is used only to find candidates for that comparison. It cannot decide the match, because an original can be named like a size: `banner-1200x400.png` is its own original and does not belong to `banner.png`. Candidates also include the `-scaled` and `-rotated` names core stores a replaced original under, since the sizes of such a record keep the original's name, and `doc.pdf` for a PDF preview named `doc-pdf.jpg`.
- **A union with `include[]`** — each parameter names records, and a consumer sends ids for the references it trusts and files for the rest. An intersection would answer a question nobody asks. A request whose `file` and `include` resolve to nothing serves nothing, by the same `has_param()` rule `include` already follows.
- **Unmatched paths are omitted** — the request succeeds, so the consumer can report exactly which references the site does not serve. A path two records share returns both.
- **At most 100 paths per request** — `AttachmentFiles::MAX_PATHS`, enforced as the parameter schema's `maxItems`, so 101 answers `400` from core's own validation and the limit is published in the route's schema. It bounds the paths, not the records: a shared file returns every record that owns it and `include` adds to the set, so a selection can need a second page. Each path expands to at most seven candidate names, which bounds the candidate query at 700 values.
- **Read through core's API** — candidates come from a `WP_Query` `meta_query` on `_wp_attached_file` with filters suppressed (D-045), and the size list from `wp_get_attachment_metadata( $id, true )`, unfiltered. No SQL.
- **Bound** — a size a record no longer lists is not matched. That covers a size generated before an image was edited in WordPress, which core moves to `_wp_attachment_backup_sizes`, and any size a plugin generated without recording it. So does a size written in a different format from its original, which happens when `image_editor_output_format` converts sizes (a `photo.jpg` whose sizes are `.webp`) or for a HEIC original stored as JPEG: candidates keep the requested extension, so the record is never found. Those references fall back to the consumer's full attachment read.
- **Ref** — #300, `UAMS-Web/wordpress-importer#1175`, D-045, #48

### D-087 — `/options` serves each active plugin's header, read from disk, beside the database fields

- **Decided** — on 2026-09-30, for #338. The `/options` response carries `plugins`: one entry per path in the site's `active_plugins` and the network's `active_sitewide_plugins`, as stored, each with `scope` (`site` or `network`) and `header`, which is `Name`, `Version` and `TextDomain` from the plugin file on disk, or `null` when no installed plugin sits at that path.
- **The one field from the disk** — every other `/options` field, and `plugins[].path` and `plugins[].scope`, describes the **database**. `plugins[].header` describes the **disk**: `get_plugins()` — the listing the network plugins screen reads, not loaded on a REST request and required explicitly, cached in a non-persistent group — decides which paths are installed, and the three fields are then read from the file with `get_file_data()` and no context, which applies no filter.
- **Declared, never inferred** — the header is not taken from `get_plugins()`'s listing because that listing is built by `get_plugin_data()`, which fills a missing `Text Domain` with the plugin's directory name. A field the file does not declare is an empty string, not `null`: the file is there.
- **Looked up, never read from the stored path** — the stored path is a key into `get_plugins()`'s listing, and a file is read only once the listing has named it, so no value in `active_plugins` can make this read a file the listing does not already name.

A plugin can filter `option_active_plugins`, and one on this network does: LearnDash v3 appends a legacy path on every request outside the plugins screen, which would be served as an active plugin missing from disk.
- **As stored** — both lists are served in stored order, and a plugin active per site and network-wide appears once under each scope. Inactive installed plugins are not served.
- **Rejected** — a separate endpoint. The fields qualify the settings `/options` already serves, and the importer already reads that response per site; the issue allowed either.
- **The stored network list too** — amended for #341. The network list was first read through `get_site_option()`, the one network-option read `NetworkOptionGuardTest` allowed, and LearnDash v3 filters that option as well (`sfwd-lms-3/includes/class-ld-lms.php`, `site_option_active_sitewide_plugins_proc`), adding `sfwd-lms/sfwd_lms.php` whenever its own entry is network-active; that path was served as a network plugin with `header: null` and counted by the denylist's provenance check. A raw query that named no watched function would otherwise have been a network read the guard could not see. A table name assembled by concatenation is beyond a token scan, and that is the guard's bound.
- **Bound** — the Feature suite primes `get_plugins()`'s cache, which is keyed per site, to decide which paths are installed, and reads headers from fixture files in this repository, so it never writes into the plugins directory of the install it runs inside; one test reads the real listing uncached. A plugin file `get_plugins()` does not list, because it has no `Name` header or sits more than one directory deep, is served with `header: null`, the same as a missing file.

- **Decided**: on 2026-10-13, for #374. `GET /redirects/redirection` and `GET /redirects/pretty-links` serve one row per rule, ordered by id ascending and paginated like every other list route. ### D-101: A job skipped by its `if:` reports success to a required check, so the kill-switch never deadlocked a merge

- **Decided**: on 2026-10-19, for #415. D-029 and D-090 recorded that a required status check stays pending forever while `RUN_REMOTE_CI` is `false`. GitHub documents the opposite. Its [troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks) page, read on 2026-10-19, says a job skipped by a conditional reports its status as `Success`, and that "successful check statuses are `success`, `skipped`, and `neutral`". A check stays `Pending` and blocks merging only when the whole workflow is skipped by a path, branch or commit-message filter, and `ci.yml`'s `pull_request` trigger, the one that reports a pull request's checks, carries none of those (its only filter, `branches: [main]`, is on `push`).
- **The hazard is the reverse of the one recorded**: every job in `ci.yml` is skipped by its `if:` while the switch is off, so a required check on any of them would pass without running and let every merge through unchecked. The same page says a job skipped because a job it `needs` failed may also not block merging, which reaches a required check on any job after the first in the chain.
- **What still holds**: D-090's conclusion that the rulesets and the kill-switch coexist. It rests on neither ruleset requiring a status check, not on any pending behavior. Requiring a check from `ci.yml` while the switch exists would gate nothing, so the chain being run and read before a merge stays the only check that the code works.
- **Corrected with it**: the `ci.yml` header and the `RUN_REMOTE_CI` bullet in `AGENTS.md`. Left as written: `.claude/history/AGENTS.md`, which quotes the instruction as it stood before #334, verbatim; and the synced `pre-merge-check` rule, whose correction is in `UAMS-Web/uams-claude-skills#267` and reaches this repository with the next sync.
- **Ref**: #415, D-029, D-090, `UAMS-Web/uams-claude-skills#165`, `UAMS-Web/uams-claude-skills#267`

### D-102: The Integration bootstrap loads `Pest.php` itself, so a mutant child's Feature tests keep their test case

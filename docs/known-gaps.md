# Known gaps

What this plugin does not yet do, or has not yet proven, and where each limit is recorded. Moved here from `AGENTS.md` under #389, unchanged, so that file stays inside Codex's read limit. Add a gap here when one is found, and remove it when it closes.

Each gap's supporting evidence: [`.claude/history/AGENTS.md`](../.claude/history/AGENTS.md#known-gaps).

- **Dropped term assignments are verified against the development network** (#73). `scripts/verify-taxonomy-coverage.php` reports every taxonomy that carries assignments on an exposed post type but is not itself exposed, per site, and exits non-zero so it can gate a migration rather than only inform one. The Feature suite cannot answer this: it runs against a rebuilt database with no term data, and `location`/`provider` are not registered in its process. The registration-shaped half that CAN run on CI is the guard in `tests/Integration/Feature/PostsEndpointTest.php`.
- **All three form plugins are served** — `/forms/gravity`, `/forms/formidable` and `/forms/ninja` (D-055). Ninja Forms is free, so it is a dev dependency loaded from `vendor/` and its tests never skip; the other two are paid and theirs do. The Ninja endpoint exists to serve the form **id**, which a `.nff` export structurally cannot carry.
- **Gravity Forms add-on feeds are served, and no real one has been read** (#80, D-056). `/forms/gravity/feeds` and `/forms/gravity/<id>/feeds` carry the configuration that says a form creates a WordPress user on submission — the one part of a form's behavior that never appears in an export, because feeds live in `gf_addon_feed` and `GFAPI::get_form()` does not read it. The development network has never had a feed add-on active, so `gf_addon_feed` does not exist there and the test bootstrap installs it; every assertion runs against fixtures this repo creates. The payload shape is proven and the content of a production feed is not. Feed `meta` is filtered through D-032's machinery, with one exemption that carries the whole endpoint: a value that is a bare field reference is never withheld by name, because User Registration stores `password` as the id of the field the password comes from and a name-only denylist withholds exactly the mapping a consumer needs.
- **Site switching is verified against the development network** (#12, D-049). `scripts/verify-site-scoping.php` asserts the switch, the payload difference, restoration on the success path, and the `409` refusal against a genuinely flagged site. It needs an install, so it never runs on CI; the Feature suite covers the same branches against a factory-built network on every run.
- **Posts, options, discovery and terms exist, and `nav_menu_item` is served by the posts endpoint.** Menus needed no endpoint of their own: `nav_menu_item` is an eligible post type and `nav_menu` an eligible taxonomy, so the whole `_menu_item_*` set and the menu slug already travel — `tests/Integration/Feature/NavMenuParityTest.php` is what proves it rather than assuming it (#9). Attachments (#8) and authors (#10) have since landed, and comments were dropped from scope deliberately rather than deferred. Gravity Forms (#11) and Formidable Forms (#1) definitions are both served, and **two of the three now have readers**: the importer sources Gravity definitions under `--source=api` (`wordpress-importer#809`) and Ninja definitions likewise (`#810`), both merged 2026-09-15. `/forms/formidable` is still read by nothing, ticketed as `wordpress-importer#811`. D-050 carries the history, including why these were built ahead of any consumer and the condition that produced this one. Entries are never served (#54, D-048).
- **Redirection and Pretty Links rules are served, read only through each plugin's own model** (#374, D-089). `/redirects/redirection` and `/redirects/pretty-links` carry one row per rule for the importer's vanity-domain redirects, and serve only where the plugin is **active on the site being read**; `/sites` reports that per site as `redirect_plugins`. Both plugins are free dev dependencies pinned to the versions the vanity installs run, so their tests never skip. No log or click table is served, and the per-rule counters derived from them are dropped. That the served count matches the plugin's own count on a real install has not been read, because neither plugin runs on the development network.
- **Post-type and taxonomy registration is process-global, not per-site.** `/post-types` and `/taxonomies` refuse `?site=` for that reason (D-034); to ask site N what it registers, call site N's own REST root.
- **Form submissions are never served, and a guard holds that line (D-048).** Not a note: Ninja Forms stores submissions as the `nf_sub` post type, so adding one string to `config/defaults.php` would have served submitted data through `GET /posts/nf_sub` with no new code. `tests/Unit/FormEntryBoundaryTest.php` fails that edit and every `GFAPI` entry method. Note the boundary is narrower than it reads — the definitions already served carry notification recipient addresses.
- **The option denylist was reviewed against one site.** The patterns are kept broader than what fires there deliberately (D-032). A credential stored under an innocent name with an innocent-looking value is undetectable by construction — that is the accepted direction of a denylist.
- **Collection queries run with `suppress_filters => true` (D-045).** A migration read sees the raw table, not a plugin's view of it — GeoTargeting WP hooks `posts_where` to remove posts from the loop, and a read that silently omits records is this repo's defining failure mode. It is not total protection: `pre_get_posts` is an action and still runs.
- **Query cost per page is flat, but only measured to 27 records** (D-045). Production, with a larger plugin set and two orders of magnitude more attachments, is unmeasured.
- **`GET /authors` reports the authors it cannot resolve** (D-047) — a post can outlive the account that wrote it, and core drops those silently. `X-WP-Total` counts only servable authors; the orphans travel on `X-UAMSWP-Orphaned-Authors` and `X-UAMSWP-Orphaned-Author-Ids`.
- **PHPStan analyzes against the 6.8.3 stubs, not 6.8.7**: no stub release tracks WordPress patch versions, so `~6.8.0` is the closest match to production (D-106). The local suite boots a 7.0.7 install and cannot see a call newer than 6.8; the remote `pest` job runs 6.8.9 and sees one only on a path a test executes.
- **`modified_after` is unverified against a real editing window.** The suite proves it filters on the GMT column with fabricated timestamps; nothing has yet re-pulled a site while someone edited it. Five concrete ways it lost or invented records were found and fixed (D-052), so the remaining gap is the live-editing case specifically, not the parameter's arithmetic.
- **Nothing mechanically checks code before a merge to `main`.** The organization rulesets require a pull request and refuse a direct push, deletion or force push, but they require no approval and no status check (D-090). CI reports and does not gate. The chain being run and read is the gate.
- **The remote `pest` job runs against a factory-built network, not a real one.** It installs a two-site test network from the WordPress test factory, like the local suite. That is by design — an Actions runner has no development install — and `scripts/verify-site-scoping.php` is what covers the real one (#12).
